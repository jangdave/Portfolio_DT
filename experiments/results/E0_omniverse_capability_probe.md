# E0. Omniverse 계열 기술이 주는 데이터 확인 (실증)

- 날짜: 2026-10-15
- 목적: Omniverse 계열 기술에서 **어떤 시뮬레이션 정보와 데이터를 실제로 받아서 쓸 수 있는지** 직접 실행해서 확인한다. (연구 R5의 일부, R1의 준비)
- 관련: [13 Omniverse 연구 계획](../../docs/13_omniverse_research.md), [14 핵심 설계](../../docs/14_sim_to_unreal_core.md)
- 코드와 원본 결과: `experiments/omniverse_probe/`

## 0. 먼저 구분: 무엇이 Omniverse Kit에서 실행한 결과인가

| 실행한 것 | 정체 | Omniverse Kit인가 |
|---|---|---|
| Warp 1.18.0 (2.1~2.5장) | NVIDIA의 GPU Python 시뮬레이션 라이브러리 | **아니다.** 독립 Python 프로세스에서 실행 |
| ovrtx 0.3.0 (2.5장) | Omniverse 렌더링 라이브러리(Python) | **아니다.** 라이브러리이며 Kit 앱이 아니다. |
| **Omniverse Kit SDK 110.4.0 (2.6~2.8장)** | Kit 앱 개발 기반 | **그렇다.** 사용자가 라이선스 약관에 동의한 뒤 설치해서 실행 |

2.1~2.5장은 "Omniverse 계열 라이브러리"의 결과, 2.6장 이후는 "**Kit 안에서 직접 확인한 결과**"다.

## 1. 환경
RTX 5090 32GB, 드라이버 CUDA 13.4, Python 3.13.9, Warp 1.18.0(CUDA Toolkit 13.4, sm_120), ovrtx 0.3.0.312915, ovphysx 0.3.7, usd-core 26.8

## 2. 결과

### 2.1 Warp가 RTX 5090에서 동작한다 (직접 확인)
- Warp가 GPU를 `sm_120`(Blackwell)으로 인식하고 커널을 컴파일해 실행했다. 첫 컴파일 0.43초, 계산 결과 일치.

### 2.2 USD 장면 위의 열 시뮬레이션과 가상 센서 (직접 확인)
`thermal_poc.py`: 랙 10기, CRAC 2기, 센서 앵커 24개가 있는 USD 장면을 직접 만들고, **그 USD에서 형상과 앵커 위치를 읽어** Warp로 계산했다.

| 항목 | 값 |
|---|---|
| 장면 | 8 x 6 x 3.5 m, 랙 2줄 x 5기, 마주 보는 찬 통로, 양 끝 CRAC 1기씩 |
| 격자 | 10 cm 간격, 80 x 60 x 35 = 168,000칸 |
| 시나리오 | 240초, 60초에 CRAC_02 팬이 멈춤 |
| 센서 ID | 규격 규칙(`H01-RK01-TEMP-IN`)대로 USD 경로에서 계산 |
| 가상 센서 | 앵커 위치에서 온도를 세 선형 보간으로 읽음, 24개 x 240초 = 5,760개 값 |

**결과(랙 입구 온도, 마지막 10초 평균, 서쪽 → 동쪽)**

| 줄 | 서쪽 ← | | | | → 동쪽 (고장난 CRAC_02 쪽) |
|---|---|---|---|---|---|
| Row01 (RK01~05) | 22.5 | 23.6 | 27.4 | 40.1 | 42.4 |
| Row02 (RK06~10) | 22.5 | 23.5 | 27.3 | 39.7 | 41.9 |

- 정상일 때(고장 전) 입구 온도 평균은 약 21.5도였다.
- **고장난 CRAC에 가까운 동쪽 랙 4기가 고장 후 6~8초 만에 27도를 넘었다.** 서쪽 랙은 CRAC_01이 작동해 22~24도로 유지됐다.
- 센서별 시계열은 `out/thermal_sensors.csv`, 온도 단면 이미지는 `out/thermal_slice_t*.png`.

**이 실험에서 찾은 문제 두 가지**
1. **센서 위치 오류(수정함):** 처음에는 모든 랙이 똑같이 31.3도로 나왔다. 앵커를 **스케일이 걸린 랙 상자의 자식**으로 만들어서 월드 좌표에 랙의 스케일이 곱해졌기 때문이다. [USD 규격](../../docs/09_usd_spec.md) 2장의 "장비는 스케일 없는 Xform, 모양은 자식 메시" 규칙이 필요한 이유를 실제로 보여 준 사례다.
2. **응답이 너무 빠르다(미해결, 한계):** 실제 시설의 열 반응은 분 단위인데 이 모델은 6~8초 만에 변한다. 시각화용으로는 시간 배율이나 열 질량 매개변수로 조정할 수 있지만 **이번에는 조정하지 않았다.**

### 2.3 계산 속도와 해상도 확장성 (직접 확인)
`bench_thermal.py`: 같은 장면을 해상도만 바꿔 GPU 동기화 후 측정했다.

| 격자 간격 | 칸 수 | 시간 간격 | 초당 단계 | 실시간 대비 |
|---|---|---|---|---|
| 10 cm | 168,000 | 0.02 s | 약 43,000 | 약 867배 |
| 5 cm | 1,344,000 | 0.01 s | 약 45,000 | 약 452배 |
| 2.5 cm | 10,752,000 | 0.0025 s | 약 5,500 | 약 13.7배 |

- 이 규모의 시뮬레이션은 GPU에게 부담이 아니다. 격자를 훨씬 촘촘하게 해도 실시간보다 빠르다.
- **찾은 문제:** 2.5 cm에서 시간 간격을 0.005초로 하니 **계산이 발산**해 NaN이 됐다. 확산의 안정 조건(`K·dt/dx²`)에 여유가 없었다(이론 한계 1/6, 실제로는 0.16에서 발산). 0.1 이하(실제 0.08)로 맞추니 안정적이다. **이 값을 규칙으로 문서화한다.**
- 계산 속도에는 GPU 캐시 효과가 섞여 있어 대역폭 같은 추정치는 이 표에 넣지 않았다.

### 2.4 NanoVDB 저장과 다시 읽기 (직접 확인)
- `wp.Volume.load_from_numpy`로 온도장을 만들고 `save_to_nvdb`로 저장, `load_from_nvdb`로 다시 읽어 복셀 수와 간격이 같음을 확인했다.
- 파일 크기 약 1.1 MB(240초 시점 한 프레임, 80 x 60 x 35, 비압축). 활성 복셀 204,800개는 8x8x8 블록 단위로 채워진 값이다. 이 장면은 꽉 찬 격자라 희소 저장의 이점은 없다.
- **Unreal에서 읽을 수 있는지는 확인하지 못했다**(R6). Warp는 OpenVDB 쓰기를 문서에서 확인하지 못했다.

### 2.6 Omniverse Kit가 RTX 5090에서 실행된다 (직접 확인, R1)
Kit App Template(NVIDIA 공식 저장소, 버전 110.4.0)로 `dctwin.base_editor` 앱을 만들고 실행했다.

| 확인한 것 | 결과 |
|---|---|
| Kit 버전과 GPU | Kit 110.4.0, RTX 5090 32GB, 드라이버 616.92, 그래픽 API D3D12 |
| 필수 확장 | `omni.hydra.rtx`(RTX 뷰포트), `omni.graph.core`(OmniGraph), `omni.warp.core`(Warp), `omni.physx.stageupdate`(PhysX)가 모두 켜짐 |
| USD 장면 열기 | 우리 `poc_hall.usda`(prim 80개, 센서 앵커 24개)를 4.2초에 열고 화면에 그림 |
| **Kit 안의 Warp** | Kit에 포함된 Warp 1.17.0이 RTX 5090(sm_120)에서 GPU 커널 실행 성공 |
| 뷰포트 화면 | `out/kit/kit_viewport.png`: 랙 5기씩 두 줄과 CRAC 2기가 보인다. |
| 시작 시간 | **첫 실행 239초**(확장을 내려받는 시간 포함), **이후 실행 12초**(RTX 준비 완료까지) |

- 템플릿의 대화형 마법사(`repo template new`)는 실제 Windows 콘솔이 필요해서 자동화 환경에서는 실행되지 않았다. 대신 템플릿의 `kit_base_editor.kit`에서 이름과 버전 자리표시자만 채워 `source/apps/dctwin.base_editor.kit`을 만들고 `repo build`로 빌드했다. 방법은 `experiments/omniverse_probe/kit/README.md`.
- 종료할 때 저장 확인 대화상자가 떠서 프로세스가 남는 문제가 있었다. `--/app/file/ignoreUnsavedOnExit=true` 옵션으로 해결했다.

### 2.7 Kit의 Flow(연기·유체) 확장 (직접 확인, R2의 일부)
| 확인한 것 | 결과 |
|---|---|
| Flow 확장 | `omni.flowusd` 110.0.4가 RTX 5090에서 켜짐(7.5초) |
| USD Flow 스키마 | 23종 등록. 이 중 **`FlowEmitterNanoVdb`(NanoVDB를 발생원으로 사용)** 와 **`FlowSparseNanoVdbExportParams`(NanoVDB 내보내기)** 가 있다. |
| 내보내기 채널 | 연기, 온도, 연료, 연소, 속도, 발산(divergence)을 고를 수 있음. `readbackOpenVDB`로 OpenVDB 파일을 디스크에 저장 |
| 코드로 만들기 | `FlowCreatePresets`(프리셋 생성) 명령. 프리셋은 `Fire` 하나가 들어 있다. |

**Flow 열 플룸 시뮬레이션과 OpenVDB 내보내기 실행 결과**
- `Fire` 프리셋으로 열 플룸을 만들고 연기, 온도, 속도 3채널을 내보냈다. **OpenVDB 파일 헤더가 올바른 `.vdb` 파일이 생성됐다**(981개, 채널당 327프레임).
- **용량이 매우 크다.** 합계 7.2GB. 파일 하나가 연기 7.7MB, 온도 15MB, 속도 8.6MB다(프레임당 3채널 합계 약 31MB). 프리셋 기본값은 시각 품질 중심이며 우리 홀 규모에 맞춘 값이 아니다.
- **프레임이 크게 떨어진다.** 내보내기를 켜면 평균 **4.8 FPS**, 끄면 안정 구간에서 약 **47.6 FPS**였다(약 10배 차이). 매 프레임 GPU에서 CPU로 읽어 OpenVDB로 변환하고 디스크에 쓰기 때문으로 보인다. 실시간 경로로는 쓸 수 없고 미리 계산하는 경로(C)로만 쓸 수 있다.
- **시각 확인:** Kit 창에서 직접 본 화면은 잘 보였다고 한다. 자동 캡처 이미지는 화면 전체가 연노랑으로 번져 **쓸 수 없어서 저장소에 올리지 않았다.** 원인은 확인하지 못했다(카메라, 프리셋 렌더 설정, 캡처 시점 중 하나로 추정만 한다). 프리셋의 중력이 Y축 아래 방향(0, -100, 0)이라 Z-up 장면에서는 방향이 맞지 않을 수 있다.
- 우리 데이터센터 열 모델과는 연결하지 않았다. 이 실험은 **Flow가 Kit에서 돌고 OpenVDB를 내보내는 경로**의 확인이다.

### 2.8 부피 데이터 용량 비교 (직접 확인)
`bench_vdb_size.py`: Warp 열 시뮬레이션의 마지막 프레임을 격자 간격과 압축 방식별로 저장했다. 다시 읽어 복셀 수가 같음을 확인했다.

| 격자 | 칸 수 | 압축 | 프레임당 용량 | 240프레임(1초당 1프레임) |
|---|---|---|---|---|
| 20 cm | 21,600 | 없음 | 424 KiB | 약 104 MB |
| 20 cm | 21,600 | **zip** | **71.5 KiB** | **약 17.6 MB** |
| 10 cm | 168,000 | 없음 | 1,136 KiB | 약 279 MB |
| 10 cm | 168,000 | zip | 494 KiB | 약 121 MB |
| (비교) Flow `Fire` 프리셋 | 해상도 큼 | 없음 | 약 31MB(3채널) | 약 7.4 GB |

- 같은 시나리오를 저장할 때 Warp 20cm + zip은 Flow 내보내기의 **수백 분의 1**이다. 우리 홀(8 x 6 x 3.5 m)에는 20cm 격자로도 센서와 열 분포를 보여 주기에 충분한지 Phase 4에서 확인한다.
- `blosc` 압축은 `blosc` Python 모듈이 없어서 시험하지 못했다.

### 2.8-2 화재, 열 전도, CFD, 그리고 다른 시뮬레이션은 가능한가 (조회와 직접 확인)
Kit 110.4.0의 확장 레지스트리 전체(685개 이름)를 `kit_list_exts.py`로 조회하고, 직접 실행해 본 것과 합쳐 정리했다. **"확장 이름에 없다"는 것이 "불가능하다"는 뜻은 아니다.** 이름 기준 조회라서 기능이 다른 이름 안에 들어 있을 수 있다.

| 질문 | 답 | 근거 |
|---|---|---|
| **화재** | **가능** (시각적 시뮬레이션) | Flow `Fire` 프리셋이 Kit에서 실행되고 연료, 연소, 온도, 연기 채널을 계산해 OpenVDB로 내보냈다(직접 확인). 공학적 화재 해석(FDS 같은 도구)은 아니다. |
| **열 전도(고체 속 열 이동)** | **Kit 기본 확장에는 없다. Warp로 직접 구현 가능** | 레지스트리에 열, 전도 확장이 없다. 직접 확인한 것은 **공기 속 열의 이동과 확산**(Warp)이고, 랙 외벽 같은 고체의 열 전도는 구현하지 않았다. 확산 계산은 이미 있어서 고체 칸에 열전도율을 주는 확장은 어렵지 않을 것으로 본다(미시험). |
| **CFD(유체 흐름 해석)** | **Kit 기본 레지스트리에는 CFD 확장이 없다. 현재 우리 모델은 CFD가 아니다.** | 우리의 L1은 "정해 둔 흐름 위의 열 이동"이다. NVIDIA의 DSX Blueprint 문서는 CFD 핫아일 시뮬레이션을 포함한다고 하며 Kit-CAE, Warp, Cadence 도구를 언급하지만 **기본 레지스트리에 `cae` 확장이 없고 직접 설치해 보지 않았다.** 공기 흐름까지 계산하는 L2는 Warp로 직접 구현해야 한다(미구현). |
| 물리(강체, 충돌, 차량) | 가능 | `omni.physx` 계열(차량, 충돌 검사, 텐서, 카메라 등)이 레지스트리에 있고 Kit 앱에 포함되어 동작한다. ovphysx 라이브러리도 있다(미시험). |
| 연기·유체 | 가능 | Flow (직접 확인) |
| 입자, 변형체, 천 | 미확인 | 입자 스키마(`usd_particle_field`)만 보인다. 변형체와 천은 이름으로 조회되지 않았다. Warp 샘플 확장(`omni.warp.samples`)에 데모가 있을 수 있다(미확인). |
| 임의의 사용자 정의 시뮬레이션 | 가능 | Warp(직접 확인). `omni.warp`, `omni.warp.graph`(OmniGraph 연동) 확장도 있다. |
| 합성 데이터 | 가능(미시험) | `omni.replicator.core` 등 Replicator 확장이 있다. 가상 CCTV 영상과 라벨을 만드는 데 쓸 수 있다. |
| 센서 시뮬레이션 | 가능(미시험) | `omni.sensors.nv`의 카메라, 라이다, 레이더, 음향 확장이 있다. |
| 전기 부하, 전력 효율 | **Omniverse 확장 없음** | 전력과 PUE는 Python으로 계산한다(집계 값). DSX 문서는 전기 시뮬레이션에 별도 도구(ETAP)를 언급한다. |
| VDB 시간 재생 | 도구 있음(미시험) | `omni.vdb_timesample_editor`가 있다. Flow의 `readbackMaterial` 설명도 재생용 시간 정보를 자동 설정한다고 한다. |

## 2.9 결론: 부피 데이터는 Warp 20cm + zip을 기본으로 한다
- **기본:** Warp가 USD 장면에서 계산한 온도장을 20cm 격자, zip 압축 NanoVDB로 저장한다. 용량이 작고(시나리오 240초에 약 18MB) 센서 값과 같은 시뮬레이션에서 나온다.
- **Flow는 연구 대상으로 유지:** 연기·열기 **시각 효과**에 쓸 수 있는지 계속 본다. 쓰려면 해상도(`densityCellSize`), 내보내는 채널(온도만), 내보내는 빈도(1초에 1번만 켜기), 정밀도(`enableLowPrecision*`)를 줄여야 한다.
- **Unreal이 읽는지는 2.10장(R6)에서 확인했다.** 단, Warp의 NanoVDB를 그대로는 못 읽고 OpenVDB로 바꿔야 한다.

### 2.10 부피 데이터를 Unreal로 보내는 경로 (직접 확인, R6)
UE 5.7.4를 명령줄(`UnrealEditor-Cmd`)로 실행해 파일을 가져오고 결과를 확인했다. 시험 전용 프로젝트(`D:/ue_probe/VdbProbe`, 저장소에 올리지 않음)에서 `InterchangeOpenVDB` 플러그인을 켰다.

**가져오기 결과**

| 파일 | 출처 | 크기 | UE 가져오기 결과 |
|---|---|---|---|
| Flow `.vdb` 3개(연기, 온도, 속도) | Kit Flow 내보내기 | 7.7MB, 15MB, 8.6MB | **성공.** `StaticSparseVolumeTexture` (연기·온도 192 x 192 x 544, 속도 96 x 96 x 272) |
| Warp NanoVDB `.nvdb` | Warp `save_to_nvdb` | 1.1MB | **실패.** 가져와지지 않음(에셋이 만들어지지 않음) |
| **Warp 결과를 OpenVDB로 변환한 `.vdb`** | Kit의 `openvdb`로 변환 | 75.8KB(float), 46KB(half) | **성공.** `StaticSparseVolumeTexture` **40 x 30 x 18**(우리 격자와 같음) |
| 번호가 연속된 `.vdb` 8개(`Temp_000` ~ `Temp_007`) | 위와 같음 | 8개 | **성공.** `AnimatedSparseVolumeTexture` **40 x 30 x 18, 8프레임.** UE가 번호를 보고 자동으로 하나로 묶음 |

**알게 된 것**
- UE 5.7의 Interchange OpenVDB 변환기는 `.vdb`를 직접 가져오도록 광고하지 않는다. 소스 주석에 "USD 변환기가 USD+OpenVDB 파일을 가져올 때만 쓰며 `.vdb`를 직접 가져오지 않는다"고 적혀 있다. 그래서 Interchange로는 "변환 불가"가 나온다. 대신 **기존 에셋 가져오기 경로(Sparse Volume Texture 팩토리)** 가 `.vdb`를 가져온다.
- **NanoVDB는 UE가 읽지 못한다.** Warp는 OpenVDB 쓰기를 지원하지 않고 설치 가능한 Python OpenVDB 패키지도 없다(`pyopenvdb`는 Python 3.13용 빌드가 없다).
- **해결: Kit에 들어 있는 `openvdb` 모듈**(`omni.volume` 확장, Python 3.12)로 변환한다. Warp 결과를 numpy 프레임으로 저장하고, Kit 안에서 `openvdb`로 `.vdb`를 쓴다.

**확정된 경로**
```
Warp 열 시뮬레이션 → numpy 프레임(export_frames.py) → Kit 안에서 openvdb로 .vdb 변환(kit_npy_to_vdb.py)
   → 번호가 연속된 파일(Temp_000.vdb ...) → UE에서 가져오기 → AnimatedSparseVolumeTexture
```

**변환 정확도와 용량(20cm 격자, 8프레임)**

| 항목 | float | half(16비트) |
|---|---|---|
| 프레임당 파일 크기 | 약 75~81 KB | 약 44~47 KB |
| 240프레임 예상 | 약 18~19 MB | 약 11 MB |
| 원본과의 최대 오차(다시 읽어 비교) | 0.009도 | 0.016도 |

- 온도 범위는 18.2~53.2도이고 오차는 센서 잡음(0.05도)보다 작다.
- 배경값(주변 공기 온도 22도)과 거의 같은 칸은 저장하지 않게(`tolerance=0.01`) 했지만 이 장면은 거의 모든 칸이 바뀌어서(활성 21,512 / 21,600칸) 희소 저장의 이점은 작다.

**아직 확인하지 못한 것**
- **UE 화면에서 실제로 그려지는 모습.** 가져오기와 크기는 확인했지만, 온도 색 변환 머티리얼은 만들지 않았다(2.11장에서 내장 뷰어로 시도).
- 가져올 때 "온도"가 어느 속성 채널로 들어갔는지(자동 가져오기 기본값을 썼다)와 값이 UE 안에서 보존되는지.
- 프레임 전환 시간, 메모리 사용량. 프레임은 8개만 시험했다.

### 2.11 UE에서 부피를 직접 보기 (진행 중)
가져온 볼륨을 UE 화면에서 보기 위해 UE 내장 **Sparse Volume Texture Viewer** 액터로 데모 레벨을 만들었다. 이 액터는 가져온 볼륨(`sparse_volume_texture_preview`), 프레임 재생(`playing`, `looping`, `frame_rate`), 보여 줄 채널(`preview_attribute`), 투명도(`extinction`), 발광 광원(`emissive_light_source`)을 설정할 수 있다. 별도 머티리얼 없이 볼륨을 볼 수 있다.

**첫 번째 시도의 결과(사용자가 에디터에서 직접 확인):** 8프레임이 **재생은 되지만 화면이 까맣게만 보였다.** 원인으로 두 가지를 찾았다. 아직 하나로 확정하지는 못했다.
1. **데이터:** 볼륨의 값이 섭씨 온도 그대로(18~53)였고 주변 공기(22도)도 값이 22라서, 화면 전체가 짙은 연기로 채워졌다. 뜨거운 곳과의 차이가 작고 전체가 불투명해졌다.
2. **카메라:** 에디터 시작 카메라가 볼륨 한가운데(원점)에 있었을 가능성이 있다. 불투명한 연기 안에 카메라가 있으면 검게 보인다.

**조치(두 번째 시도):**
- 온도를 **0~1로 정규화**하고 주변 공기를 0(빈 공간)으로 바꿨다: `value = clip((T - 24) / (54 - 24), 0, 1)`. 24도 이하는 저장하지 않는다. 우리 데이터 규격이 원래 정한 방식(값 정규화)이기도 하다. 희소 저장의 효과도 생겼다(30초 시점 21,600칸 중 6,588칸만 활성, 파일 35KB).
- 볼륨을 원점에서 떨어뜨리고, 홀을 비스듬히 보는 카메라 액터(`Cam_Hall`)를 추가했다.
- 투명도와 발광이 다른 레벨 3개(`VolumeDemo_A`, `_B`, `_C`)를 만들었다. A: 발광 끔, B: 발광 켬, C: 투명도 낮게와 발광 켬.

**한계:**
- **자동 화면 캡처는 되지 않았다.** UE를 화면 없이 돌리면 뷰포트가 그려지지 않아 스크린샷 파일이 만들어지지 않는다. 그래서 시각 확인은 **사용자가 에디터에서 직접 본 결과**에 의존한다.
- 이 뷰어는 확인용이다. 온도를 **색 변환(파랑→노랑→빨강)** 으로 보여 주려면 볼륨 머티리얼을 직접 만들어야 한다(Phase 4).
- 레벨 C는 생성 기록(JSON)에 남지 않았다. 파일은 만들어졌지만 내용을 확인하지 못했다.

### 2.12 화면이 선명하지 않은 원인과 전용 볼륨 머티리얼 (진행 중)
**관찰(사용자):** 내장 뷰어로 정규화한 볼륨을 보니 변화는 보이지만 선명하게 보이지 않는다.

**원인 후보** (아직 어느 하나로 확정하지 못했다)
1. **내장 뷰어에는 색 변환이 없다.** 값을 선형 흑백 농도로만 보여 주고 대비와 색을 조절할 수 없다. 볼륨 렌더링은 값을 색과 불투명도로 바꾸는 머티리얼(트랜스퍼 펑션)이 있어야 선명해진다.
2. **데이터가 본래 매끄럽다.** 열 확산과 이류 계산은 경계를 부드럽게 만들고, 20cm 격자(셀 하나가 20cm)를 3선형 보간으로 그리면 경계가 더 흐려진다.
3. **값이 중간 구간에 몰린다.** 24~54도를 0~1로 정규화하면 대부분의 값이 0.1~0.5에 모여 대비가 약하다. 알람 기준(주의 27도 = 0.10, 위험 32도 = 0.267)에 맞춘 색 구간이 필요하다.
4. 조명 의존: 볼륨이 빛을 받아야 보이는 구조라 조명이 약하면 어둡다. 발광을 넣으면 해결된다.

**실무에서 알려진 같은 증상(일반화한 교훈)**
- 전용 볼륨 머티리얼 없이 기본 머티리얼로 보면 매끄러운 반투명 연기가 아니라 **각진 불투명 덩어리**로 보인다.
- **저장 단계에서 값이 이미 거의 최대로 눌려 있으면 머티리얼로 고칠 수 없다.** 값의 분포를 먼저 확인하고 정규화 범위를 데이터에 맞춰야 한다.
- 색 구간은 알람 기준과 **같은 값**으로 맞춘다.

**조치**
| 항목 | 이전 | 변경 |
|---|---|---|
| 격자 해상도 | 20cm (40 x 30 x 18) | **10cm (80 x 60 x 35)**. OpenVDB 프레임당 237~499KB, 8프레임 SVT 에셋 818KB |
| 표현 | 내장 뷰어(흑백 농도) | **전용 Volume 머티리얼** + `HeterogeneousVolume` 액터 |
| 색 | 없음 | 파랑 → 노랑(주의, 0.10) → 빨강(위험, 0.267) → 흰색 |
| 불투명도 | 값 x 고정 배율 | `extinction = v^Contrast x DensityScale` (머티리얼 인스턴스 파라미터로 실시간 조절, 기본 DensityScale 0.004) |
| 발광 | 끔/켬 | `색 x v x EmissiveGain` (어두운 환경에서도 뜨거운 곳이 보임) |

**스크립트로 확인한 것:** 볼륨 가져오기(80 x 60 x 35, 8프레임), 머티리얼 생성(볼륨 샘플 노드 연결 성공), 액터 속성 설정, 레벨 저장이 모두 성공했다. **화면에 실제로 어떻게 보이는지는 사용자 확인 대기 중이다**(자동 캡처가 안 된다).

**조절 방법:** 에디터에서 `MI_TempVolume`을 열어 `DensityScale`(투명도), `Contrast`(대비), `EmissiveGain`(발광)을 바꾸면 바로 반영된다.

**첫 전용 머티리얼 시도의 결과: "작고 검은 네모 상자만 보임"(사용자 확인)**
- 원인으로 확인한 것: `HeterogeneousVolume`의 **영역은 SVT 크기가 아니라 액터 스케일이 정하는 상자**다(기본 1 x 1 x 1 단위 상자, 중심 기준). 한 칸 크기(10cm)를 균등 배율로 넣어서 영역이 **10cm 정육면체**가 되었다. 내장 뷰어는 SVT 크기를 따라가서 이 문제가 없었다.
- 조치(이후 틀린 것으로 확인되어 2.16장에서 다시 고침): 액터 스케일을 홀 크기 (800, 600, 350)cm로 하고 홀 중심에 놓았다. 영역이 커진 만큼 광학 두께가 늘어나므로 `DensityScale` 기본값을 0.02에서 0.004로 낮췄다(홀 폭 600cm에서 값 0.5일 때 광학 두께 약 1.2).
- 이 수정본(`HeatDemo2` 프로젝트)의 화면은 사용자 확인 대기 중이다.

### 2.13 기본 Sparse 머티리얼의 파라미터 이름과 축 방향 비교 (진행 중)
**"완전 이상하게 보인다"는 관찰(사용자)** 에 대해 엔진 소스와 기존 실무 기록을 확인했다.

**엔진 소스로 확인한 사실 (UE 5.7.4)**
- 엔진 기본 Sparse Volume 머티리얼은 `/Engine/EngineMaterials/SparseVolumeMaterial`이고, 머티리얼 인스턴스 팩토리가 **SVT 파라미터 이름 `SparseVolumeTexture`** 로 볼륨을 넣는다. 기본 머티리얼을 쓰려면 파라미터 이름이 이것이어야 한다.
- 기본 머티리얼 팩토리는 볼륨의 **Attributes A를 발광 색(RGB)** 에, **Attributes B를 서브서피스 색**에 그대로 연결한다. 우리 데이터는 R 채널(정규화한 온도) 하나뿐이라, 기본 머티리얼로는 붉은 단색 농도로만 보인다(색 변환과 불투명도 조절 없음).
- `HeterogeneousVolumeComponent`는 머티리얼 안의 **SVT 파라미터를 이름과 무관하게 찾아서**(`GetAllSparseVolumeTextureParameterInfo`) 매 프레임 현재 프레임을 넣는다. 따라서 파라미터 **노드**(`SparseVolumeTextureObjectParameter`)여야 하고, 일반 오브젝트 노드는 안 된다. 우리 머티리얼의 파라미터 이름도 `SparseVolumeTexture`로 통일했다.
- 뷰어(`SparseVolumeTextureViewer`)는 머티리얼이 아니라 렌더러 안의 확인용 시각화라서 파라미터 이름과 무관하다.

**기존 실무 기록에서 얻은 일반화한 교훈** (회사 이름과 내부 값은 쓰지 않았다)
- **UE의 SVT 임포터는 VDB 변환의 부호를 무시하고 격자 인덱스를 그대로 쓴다.** 그래서 모델과 맞추려면 데이터 배열을 **한 축 기준으로 직접 뒤집어야** 하는 경우가 있었다(어느 축인지는 모델에 따라 달랐고 눈으로 확인했다). 우리 화면이 거울상일 가능성이 있다.
- 저장 단계에서 값이 이미 눌려 있으면 머티리얼로 고칠 수 없다(2.12장).
- 낮은 값의 발광을 0으로 두면 저온 영역이 어둡게 나오고, 데이터가 없는 빈 곳까지 발광 번짐이 생기지 않도록 데이터 마스크를 함께 써야 한다.
- 데이터 문제(이상값 구간)와 렌더링 문제를 구분해서 진단해야 한다. 정상 데이터가 정상적으로 칠해진 것을 렌더링 오류로 오해한 사례가 있었다.

**비교용 데모 레벨 (`HeatDemo3` 프로젝트)**: 같은 데이터를 축 방향만 다르게 만들어 **실제 랙 10기와 CRAC 2기 위치의 상자와 함께** 보여 준다.
| 레벨 | 데이터 |
|---|---|
| `HeatDemo_N` | 원본 |
| `HeatDemo_FX` | X축을 뒤집은 데이터 |
| `HeatDemo_FY` | Y축을 뒤집은 데이터 (이 장면은 Y 방향으로 대칭이라 원본과 구분이 어려울 수 있다) |

**맞는 모습의 기준:** CRAC_02(동쪽, 오른쪽 끝)가 60초에 고장이므로 시간이 지나면 **동쪽 CRAC 쪽에서 열이 커지고**, CRAC_01(서쪽) 쪽은 차갑게 남는다. 뜨거운 공기는 랙 뒤쪽 통로와 천장 쪽에 모인다. 이 기준과 맞는 레벨이 정답이다.

**확인 대기 중:** 어느 레벨이 맞는지는 사용자 확인이 필요하다.

### 2.14 기존 업무 볼륨 머티리얼로 시험 (로컬 시험, 에셋은 저장소에 없음)
기존 업무 프로젝트의 볼륨 머티리얼을 시험 전용 프로젝트에 복사해(머티리얼과 인스턴스 2개만, 저장소에는 올리지 않음) 우리 볼륨을 연결해 봤다. 그 머티리얼의 구성은 이 프로젝트의 설계에 참고할 만한 점이 많다.

**확인한 규약 (일반화)**
- **VDB에 저장하는 값의 범위가 고정**되어 있다(0~60도 → `value = T / 60`). 머티리얼이 이 범위를 알고 실제 온도를 복원한 뒤, **표시 범위**(데이터셋마다 다른 최소/최대 온도)로 다시 정규화해서 색과 불투명도에 쓴다. 저장 범위는 모든 데이터가 공통, 표시 범위는 데이터마다 조절하는 구조다.
- SVT 파라미터 이름은 엔진 기본 규칙(`SparseVolumeTexture`)을 따른다.
- 색은 6단계 램프, 불투명도에는 대비, 최대 한계, 데이터가 없는 곳을 가리는 마스크가 있고, 발광에는 최소 바닥값이 있다.
- 머티리얼 인스턴스의 SVT 값은 **Python으로 지정할 수 있다**(구조체 `SparseVolumeTextureParameterValue`의 `parameter_info`와 `parameter_value`). 에셋을 직접 열지 않아도 자동화가 가능하다.

**우리 데이터에 적용:** 같은 열 시뮬레이션 프레임을 `T / 60` 규약으로 다시 변환하고(활성 칸이 모두 채워져 프레임당 약 505~518KB), 머티리얼 인스턴스의 표시 범위를 24~54도로 설정했다. 원본과 X, Y 축 뒤집기 세 변형을 같은 실제 장비 위치 상자와 함께 놓았다.

**결과(사용자 확인):** 기존 업무 프로젝트에서 보던 것과 **같은 모습으로 표시된다.** 즉 Warp 열 시뮬레이션 → Kit의 `openvdb` 변환 → UE의 애니메이션 볼륨 → 전용 볼륨 머티리얼로 이어지는 **전체 경로가 화면까지 동작한다.** (레벨 생성과 SVT 연결은 스크립트로도 확인했다.)

**아직 정하지 못한 것:** 원본, X 뒤집기, Y 뒤집기 중 **어느 축 방향이 실제 장비 위치와 맞는지**는 사용자 확인이 필요하다. 이 장면은 Y 방향으로 대칭이라 Y 뒤집기는 구분이 어렵다.

### 2.15 온도의 "방향성" 표시 가능성 검토
**질문:** 온도가 어느 방향으로 이동하는지도 화면에 보여 줄 수 있는가?

"방향성"은 네 가지로 나뉜다. 각각 필요한 데이터와 표현 방법이 다르다.

| 방향성의 종류 | 필요한 데이터 | 우리 모델에서 얻을 수 있는가 | 표현 방법 |
|---|---|---|---|
| **① 공기 흐름 방향** (열을 실어 나르는 방향) | 속도 벡터장 | **가능**(실측). 단, 정해 둔 흐름이다. | 화살표(인스턴스 메시) **[1순위]**, 입자와 스트림라인(나이아가라) [후속] |
| **② 열이 번지는 순서와 방향** (어디서 시작해 어디로 퍼지는가) | 도달 시간(처음 기준 이상이 된 시각) | **가능**(실측) | 볼륨의 도달 시간 채널로 색 등고선, 시간 순서대로 드러나는 효과 **[1순위]** |
| ③ 열 이동 경향 (`-∇T`, 높은 쪽에서 낮은 쪽) | 온도 기울기 | **가능**(실측). 단 의미가 약하다. | 화살표 [보조] |
| ④ 순환(토출 → 가열 → 상승 → 귀환) | 순환하는 흐름 | **현재 모델로는 불가** | 스트림라인. 흐름 자체를 순환하게 만들어야 한다 |

**우리 Warp 모델에서 실제로 뽑아 본 결과** (`export_direction_fields.py`, 80 x 60 x 35 격자)
- **① 속도장:** 고장 전과 후의 벡터를 저장했다. 찬 통로 동쪽(CRAC_02 쪽)의 평균 속도가 고장 전 (-0.72, 0, -0.1) m/s에서 **고장 후 (0, 0, -0.1)** 로 바뀌고(팬 정지로 가로 흐름이 사라짐), 서쪽은 (0.72, 0, -0.1)로 유지되며, 뜨거운 통로는 (0, 0, 0.4)로 위로 올라간다. 설계한 흐름이 그대로 나온다.
- **② 도달 시간:** 처음 27도 이상이 된 시각은 뜨거운 통로가 **1초부터** 넘어서 고장의 영향이 묻힌다. **고장 직전(60초) 대비 +3도**로 기준을 바꾸면 영향이 선명하다. 동쪽 절반은 100%가 도달(중앙값 34초), 서쪽 절반은 51.3%(중앙값 52초)이고, 도달한 칸의 평균 x 위치가 고장 후 5초에 5.1m, 20초에 5.8m, 120초에 2.2m로 **동쪽에서 서쪽으로 이동**한다.
- **③ 기울기:** 최대 크기 약 49 K/m, 중앙값 약 4.3 K/m. 계산은 간단하다.
- **화살표 표본:** 40cm 간격 정규 격자에서 속력 0.05 m/s 이상인 곳 2,300개(랙 내부 200개 포함)를 JSON으로 저장했다.

**기존 업무 프로젝트에서 얻은 일반화한 교훈**
- **볼륨 안에서 방향 데이터로 줄무늬가 흐르게 하는 방식은 칸마다 미세한 방향 편차 때문에 노이즈처럼 보여서 폐기**하고 화살표 방식을 채택했다.
- 화살표는 **크기 = 유속, 색 = 온도**로 역할을 분리하고, 색 램프는 볼륨과 같은 것을 써서 직접 비교되게 했다. 유속 분포가 한쪽으로 치우쳐 크기가 비슷해 보이면 **백분위 순위**로 정규화한다.
- 화살표는 **정규 격자(연속성)** 를 기본으로 하고 **소수의 극값 지점(강조)** 을 더한다. 밀도는 방 크기에 비례해 자동으로 맞춘다.
- 화살표 메시의 전방축이 코드의 가정과 달라서 회전 보정이 필요했다.
- **퍼지는 순서(도달 시간)** 를 볼륨 채널로 넣으면 번지는 효과를 줄 수 있다. 무방향 그래프의 최단 거리는 **순환을 표현할 수 없어서** 속도 벡터를 따라가는 스트림라인으로 바꿨다.
- 방향 성분을 볼륨 채널에 넣어도 결국 쓰이지 않았다. 방향은 별도 데이터(화살표 표본)로 두는 편이 낫다.

**제안하는 데이터 구성**
| 위치 | 내용 |
|---|---|
| 볼륨 채널 R | 온도 (`T/60`, 고정 범위) |
| 볼륨 채널 G | 도달 시간 (고장 후 경과 시간, 0~1) |
| 볼륨 채널 B | 속력 (정규화) |
| 별도 데이터(JSON) | 화살표 표본: 위치, 방향, 속력, 온도 |

**주의와 한계**
- **우리 모델의 공기 흐름은 영역별로 정해 둔 값이다.** 화살표는 "계산된 물리"가 아니라 **"모델이 가정한 흐름"** 을 보여 준다. 화면과 문서에 시각화용임을 밝혀야 한다. 실제로 계산한 흐름(L2)이 없이는 순환(④)은 만들 수 없다.
- 도달 시간과 기울기는 계산 결과지만 모델 자체가 시각화용이다.
- **볼륨 다중 채널 자동 가져오기(채널 매핑)는 시험하지 않았다.** 필요하면 가져올 때 채널을 지정해야 할 수 있다.
- **시간에 따라 변하는 화살표**(프레임마다 갱신)는 UE Python으로는 정적인 한 장면만 만들 수 있고, 재생 중 갱신은 C++나 블루프린트가 필요하다(Phase 5). 속도장이 팬 상태(0 또는 1)에만 의존하므로 저장할 상태는 적다.

**권장 순서:** ② 도달 시간 채널 → ① 공기 흐름 화살표 → (L2 이후) ④ 스트림라인.

### 2.16 볼륨 크기가 장비와 맞지 않았던 원인과 수정
**관찰(사용자):** 원본, X 뒤집기, Y 뒤집기 세 레벨 모두 볼륨 크기가 장비 크기와 맞지 않았다. 즉 문제는 축 방향이 아니라 **영역(크기와 위치)** 이었다.

**원인 (엔진 소스 `HeterogeneousVolumeComponent.cpp`와 UE에서 직접 읽은 값으로 확인)**
- 볼륨 영역은 **로컬 좌표 `0 ~ 복셀 수`** (가운데 기준이 아니라 **최소 모서리 기준**)에서 시작하고, 여기에 **SVT 프레임의 변환(`FrameTransform`)** 과 액터 스케일이 곱해진다.
- `FrameTransform`은 **VDB에 저장한 변환**에서 온다. 변환 부호는 무시되지만 **스케일과 이동은 쓰인다**.
- 처음에는 VDB 변환을 **미터(복셀 0.1)** 로 저장했고, UE에서 읽은 프레임 변환의 스케일이 0.1이었다. 여기에 액터 스케일을 (800, 600, 350)으로 주어 영역이 `80 x 0.1 x 800 = 6,400cm`(홀 폭의 8배)가 되었고, 액터를 홀 **가운데**에 놓아서 위치도 어긋났다.

**수정**
- VDB 변환을 **cm 단위**로 저장한다(복셀 10cm → 스케일 10).
- 액터 스케일은 **1**, 위치는 홀의 **최소 모서리(0, 0, 0)** 로 둔다.
- 확인: 새로 가져온 SVT 프레임의 `FrameTransform`이 **스케일 10.0, 이동 0, 회전 0**으로 읽혔다. 그러면 영역은 800 x 600 x 350cm로 홀과 같다.

**교훈 (일반화)**
- 볼륨 데이터를 UE로 보낼 때는 **실제 단위(cm)로 변환을 저장하고 액터 스케일은 1**로 두는 것이 가장 단순하고 오류가 적다. 이 규칙을 변환 파이프라인의 기본으로 한다.
- 액터 영역의 `get_actor_bounds`는 **재생이 시작되기 전**에는 기본값(128 복셀 기준)이라 믿을 수 없다. 값은 SVT 프레임의 `FrameTransform`과 크기로 계산해야 한다.

### 2.17 공기 순환 표현 시험 (`circulation_poc.py`)
공조기마다 공기가 어디서 시작해 어디서 끝나는지(순환의 시작과 끝)를 화면에 그릴 수 있는지 확인했다. 같은 격자(80×60×35)에서 두 가지 공기 흐름을 비교했다.
- **A. 현재 모델(정해 둔 흐름)**: 영역마다 정한 속도 값.
- **B. 질량 보존 흐름**: 공급구와 랙 뒷면을 "내보내는 곳", 랙 앞면과 회수구를 "빨아들이는 곳"으로 두고 `∇²φ = s`, `u = ∇φ`를 풀어 얻은 흐름. 점성, 난류, 부력이 없는 단순 모델이라 **순환 구조를 보여 주기 위한 용도**이며 공학적 CFD가 아니다.

공급구에서 유선 20개씩 출발시키고, 랙 앞면 30cm 앞에서 거꾸로 거슬러 올라가 공기의 출처를 분류했다.

| 시나리오 | 공급구 출발 유선이 회수구에 도달 | 랙 앞면 공기의 출처 |
|---|---|---|
| A 정상 | CRAC_01 0/20, CRAC_02 0/20 (모두 홀 밖으로 나감) | 분류 불가(재순환 100%로 잘못 분류됨) |
| B 정상 | CRAC_01 17/20, CRAC_02 17/20 (자기 회수구) | 서쪽 랙: CRAC_01 44%, 재순환 44% / 동쪽 랙: CRAC_02 67%, 재순환 33% |
| B CRAC_02 정지 | CRAC_01 17/20 | 동쪽 랙: **재순환 100%**, 서쪽 랙은 정상과 같음 |

- **결론**: 현재 모델(A)은 순환이 닫히지 않아 "시작과 끝"을 그릴 수 없다. B로 바꾸면 공급 → 랙 → 회수 순환, CRAC별 담당 영역, 고장 시 재순환(뜨거운 공기가 다시 앞면으로 들어옴)을 유선으로 보여 줄 수 있다. 평균 발산은 약 0.08 /s, 최대 속도는 3.5 m/s로 정해 둔 값(0.8 m/s)보다 크므로 공급·흡입 원천 크기 보정이 필요하다.
- **UE 표현 후보**: 유선을 스플라인/리본으로 그리고, 시작은 공급 마커, 끝은 회수 마커, 색은 CRAC별로 구분한다.
- **시험 중 고친 오류**: 처음에는 랙이 줄로 붙어 있어 연결 영역 분석이 랙 2줄을 한 덩어리로 묶었고, 시드가 6개뿐이라 출처 비율이 의미 없었다. 랙마다 시드를 만들고 앞면에서 3칸 띄워 다시 계산했다. 앞면 바로 옆 칸은 경계 영향으로 흐름 방향이 틀어졌다.
- **한계**: 순수 퍼텐셜 흐름은 관성이 없어 공급 기류가 멀리 뻗지 못한다. 천장 쪽 경계에서 끝나는 유선은 "알 수 없음"으로 센다.
- 이미지: `out/circulation/streamlines_{A,B}_{normal,crac02_off}_{top,side}.png`, 수치: `out/circulation/circulation_stats.json`.

### 2.18 랙 60기 홀 시뮬레이션 (`hall60_sim.py`)
`usd/scenes/hall01.usda`(랙 60기, CRAC 8기, 급기구 30개, 격벽 16개)를 읽어 열 시뮬레이션을 돌렸다. 랙과 CRAC의 위치, 앞면 방향, 급기구, 격벽, 홀 크기를 **장면에서 읽고 코드에는 배치를 적지 않았다.** 장면을 다시 만들면 다른 배치도 같은 방식으로 계산된다. 시각화 목적이며 공학적 CFD가 아니다.

**모델**
- 공기 흐름: 질량 보존 퍼텐셜 흐름(2.17장과 같은 방식). 급기구와 랙 뒷면은 내보내고, 랙 앞면과 CRAC 회수면은 빨아들인다.
- 통로별 균형: 뜨거운 통로의 배기를 그 통로 끝의 켜진 CRAC들이 나눠 맡는다. CRAC 용량은 가장 바쁜 통로를 정상 상태에서 감당하는 값(9.6 m³/s)이다. 용량을 넘는 배기는 격벽 지붕 틈으로 새서 방 공기에 섞인다(처음에는 이 균형이 없어서 안쪽 통로 배기 19.2 m³/s에 회수 14.4 m³/s뿐이었고, 고장 영향이 거의 안 보였다).
- 온도: Warp 이류 + 확산 + 랙 발열(10 kW, 랙 안 공기 온도 상승 = P / (ρ·cp·q)). 급기구 온도 18도 고정. `--slow 10`은 응답을 늦추는 **조절값**이며 측정값이 아니다.

- 줄 끝 랙이 더 뜨거운 것은 줄 끝 랙의 위치가 열 관리에 크게 영향을 준다는 CFD 연구(조사 자료 참고)와 방향이 같다. 이 모델이 그 연구를 재현한다고 주장하지 않는다.

**Unreal 연동 시험 (UE 5.8.3)**
- 프레임 30개를 VDB(15~45도를 0~1로 저장)로 바꾸고 `AnimatedSparseVolumeTexture`로 가져와 전용 볼륨 머티리얼, 레벨을 만들었다(`ue/run_hall60_demo.ps1`).
- 같은 장면을 USD Stage 액터로 열면 Y 부호가 뒤집힌다(ADR-010). 그래서 볼륨은 Y를 뒤집은 데이터를 쓰고 y = -1360 cm에 놓는다. 화면 확인은 사용자 에디터에서 해야 한다.

**한계**
- 점성, 난류, 부력이 없는 퍼텐셜 흐름이라 공급 기류가 멀리 뻗지 못한다. 격벽 틈과 바닥 아래 공기는 단순화했다.
- **수치 확산이 설정한 확산 계수보다 크다**(재검토에서 확인, 2026-10-16). 이류를 선형 보간으로 계산해서 유효 확산 계수가 대략 `u x dx / 2`다. 격자 0.1 m에서 흐름 1 m/s이면 0.048 m2/s로 설정한 `K_DIFF`(0.02)의 2.4배, 2 m/s이면 4.6배, 4 m/s(랙 앞 흡입 구간)이면 8.4배다(1차원 실험으로 이론식과 일치 확인). 시간 간격을 줄여도 거의 줄지 않는 방식 고유의 성질이다. 그래서 온도장은 설정값보다 흐리게 번지고, 랙 입구 온도의 높낮이 차이는 실제 흐름에서보다 작게 나올 수 있다. 고차 이류(MacCormack 등)로 바꾸면 줄일 수 있다.
- 응답 속도는 조절값이다. CRAC 팬 속도와 냉각 용량은 켜짐과 꺼짐만 다룬다.
- 외부 솔버(FDS, OpenFOAM) 결과와 비교하지 않았다. 다음 단계에서 같은 격자 `.npy` 형식으로 붙인다(ADR-009).

### 2.19 이류 방식 비교: 선형 보간과 MacCormack (2026-10-16)
2.18장의 수치 확산(선형 보간 이류가 온도를 설정보다 더 흐리게 번지게 한다)을 줄이려고 **MacCormack 이류**(앞으로 갔다 되돌아와 오차를 구해 절반을 보정하고, 결과를 출발 지점 주변 8칸의 최솟값과 최댓값으로 자르는 방식)를 넣었다. `hall60_sim.py --advection linear|maccormack`, 기본값은 `maccormack`.

**1) 이류만 계산하는 단위 시험** (`tests/test_advection.py`, 확산 0, 균일한 흐름, 폭 3칸 가우스 덩어리를 40칸 옮김, 격자 0.1 m, 시간 간격 0.04초)

| 흐름 속도 | 처음 폭(칸) / 봉우리 | 선형: 폭 / 봉우리 | MacCormack: 폭 / 봉우리 |
|---|---|---|---|
| 0.5 m/s | 3.00 / 10.00 | 6.41 / 4.68 | 3.57 / 8.22 |
| 1.0 m/s | 3.00 / 10.00 | 5.74 / 5.22 | 3.46 / 8.48 |
| 2.0 m/s | 3.00 / 10.00 | 4.12 / 7.27 | 3.13 / 9.13 |

정답은 폭 3.00, 봉우리 10.00이다. MacCormack은 새 극값(처음 최솟값 아래, 최댓값 위)을 만들지 않고(시험으로 확인), 덩어리가 옮겨 가는 속도도 맞다(오차 3% 이내).

**2) 랙 60기 홀, CRAC_02 + CRAC_06 정지, 900초** (같은 입력, `--slow 10`)

| 항목 | 선형 | MacCormack |
|---|---|---|
| 정지 직전(60초) 랙 입구 평균 | 18.42도 | 18.09도(급기 18도에 가까움) |
| 900초 랙 입구 평균 / 최대 | 19.98 / 23.44도 | 19.34 / 23.68도 |
| 줄 끝 랙 평균 / 가운데 랙 평균 | 22.43 / 19.37도 | 22.31 / 18.59도 |
| 줄 끝과 가운데의 차 | 3.06 K | 3.72 K |
| 계산 시간(900초 시뮬레이션) | 5.1초 | 4.5초 |

해석: 선형 방식은 찬 공기와 더운 공기를 수치적으로 섞어 **가운데 랙이 더 덥게, 줄 끝과 가운데의 차가 작게** 나왔다. 정지 전에도 입구가 급기 온도보다 0.4도 높았다. MacCormack은 이 오차를 줄였다. 이전에 보고한 "랙 입구 온도의 높낮이"는 **작게 나온 값**이었다. 속도는 오히려 약간 빨랐다(커널 2개를 쓰지만 같은 자릿수).

**한계:** 기준 해(OpenFOAM 등)와 비교하지 않았다. 덩어리 시험은 이류만 본 것이고 홀 결과의 정확도를 보증하지 않는다. 공기 흐름 자체(퍼텐셜 흐름, 난류와 부력 없음)의 한계는 그대로다.

### 2.20 랙 배치를 바꿔 다시 계산하기 (2026-10-16, `layout_whatif.py`)
사용자 요구: Unreal에서 랙 배치를 바꾸고 바뀐 배치로 시뮬레이션을 다시 돌린다. 시뮬레이션은 장면 USD에서 랙 위치를 읽으므로(코드에 배치를 적지 않음) **장면의 랙 위치만 바뀐 USD가 있으면 같은 코드로 다시 계산된다.** Unreal 없이 이 흐름을 확인하는 도구를 만들었다.

```
uv run --python 3.13 python layout_whatif.py --edit '{"remove": ["Rack_55"], "move": {"Rack_15": [0, 10, 0]}}' [--duration 900] [--fail CRAC_02,CRAC_06]
```
- 원본 장면은 바꾸지 않고 복사본(`out/whatif/scene_edit.usda`, 참조를 풀어 한 파일)에서 랙을 옮기거나(`move`, cm) 뺀다(`remove`). 옮긴 자리가 다른 랙이나 CRAC와 겹치면 거부한다(겹치면 한 장비가 다른 장비를 덮어써서 결과가 틀린다).
- 같은 시뮬레이션을 원래 배치와 바뀐 배치로 돌려 **랙 입구 온도의 차이**를 낸다. 계산 시간은 한 번에 약 5~15초(RTX 5090).

**시험으로 찾아 고친 문제 3건**
1. 랙 이동이 조용히 적용되지 않았다: 랙은 이동과 회전 연산을 함께 써서 `UsdGeom.XformCommonAPI`가 경고만 내고 아무것도 하지 않았다. 이동 연산(`xformOp:translate`)을 직접 바꾸도록 했다(시험이 잡음).
2. 랙을 빼면 요약 통계가 멈췄다: 줄 위치를 "랙 60기, 줄마다 10기"로 가정했다. 장면의 위치로 줄과 양 끝 랙을 정하도록 했다.
3. 랙 하나를 빼면 **멀리 있는 랙까지** 0.5도 안팎 달라졌다: 랙 흡입, 배기와 급기구의 유량을 홀 전체가 똑같이 나눠 가졌기 때문이다. 이제 랙마다(흡입면, 배기면 칸이 그 랙의 유량을 나눔), 차가운 통로마다(그 통로를 향한 랙의 유량 비율로 급기를 나눔) 원천을 만든다. 바뀐 랙 수가 11기에서 4기로 줄었고, 달라진 랙이 빠진 랙 근처(같은 줄과 마주 보는 줄)에 모였다. 원래 배치 결과는 그대로다(평균 19.34, 최대 23.68도).

**결과 예시** (CRAC_02 + CRAC_06 정지, 900초, 랙 입구 센서 위치의 마지막 값, 원래 입구 평균 18.94도, 최대 23.88도)

| 편집 | 입구 평균 | 최대 | 0.3도 이상 달라진 랙 |
|---|---|---|---|
| Rack_55 제거 | 19.05도 | 23.97도 | 4기: Rack_60 +0.61, Rack_56 +0.59, Rack_50 +0.52, Rack_51 +0.39 |
| Rack_05, Rack_06 제거 | 19.16도 | 24.11도 | 15기: Rack_01 +1.08, Rack_10 +1.04, Rack_20 +0.85, Rack_11 +0.72 등 |

랙을 빼면 이웃 랙의 입구가 **더 더워진다**(빈 자리로 뜨거운 공기가 돌아 들어옴). 방향은 현실의 경험과 맞지만 크기는 검증하지 않았다.

**한계:** 기준 해(OpenFOAM)와 비교하지 않았다. 랙 전력은 모두 같은 값(10 kW)이다. **CRAC 용량은 배치에서 계산한다**(가장 바쁜 통로를 정상 상태에서 감당하는 값, 지금 9.6 m3/s). 그래서 가장 바쁜 통로의 랙을 여러 대 빼면 CRAC 용량이 줄어드는 인공적 효과가 생긴다. 실제 CRAC 용량은 장비 사양으로 고정이므로, 배치를 자주 바꾸려면 용량을 설정값으로 빼야 한다(후속 과제). Unreal에서 장면을 저장하는 단계(편집한 USD를 내보내기)는 아직 연결하지 않았다.

### 2.21 OpenFOAM 비교에서 찾은 열 손실 고치기 (2026-10-16)
OpenFOAM 기준 답(`experiments/openfoam_baseline/`)과 비교하니 CRAC 2대 정지에서 우리 솔버가 열 쏠림을 크게 작게 봤다(최대 23.7도 대 30.9도). 두 결과의 **온도 분포와 에너지 수지**를 비교해 원인을 찾았다.

**원인:** 격벽 지붕 틈으로 새는 공기를 "아래에서 빨아들이고 위에서 내보내는" 원천 쌍으로 만들었는데, 내보내는 칸이 빨려 들어간 공기의 온도를 모르고 **주변 온도**가 됐다. 통로 1에서 틈 아래 평균 30.2도의 공기가 위에서는 24.0도로 나왔다(OpenFOAM은 31.13도에서 31.15도로 보존). 새는 유량 19.2 m3/s로 계산하면 약 140 kW의 열이 사라진다. CRAC로 나가는 열이 발열 600 kW 중 약 500 kW뿐이었고(OpenFOAM은 600 kW), 방 윗부분이 실제보다 7도쯤 차가웠다.

**고침:** 틈 위로 나오는 칸의 온도를 아래로 빨려 들어간 칸의 평균으로 맞춘다(`leak_sum_kernel`, `leak_apply_kernel`, 새지 않는 통로는 건드리지 않음). 시험: `tests/test_leak_heat.py`(고치기 전 코드에서 실패하는 것을 확인).

**결과** (CRAC_02 + CRAC_06 정지, 같은 OpenFOAM 기준 답과 비교)

| 항목 | 고치기 전 | 고친 뒤 | OpenFOAM |
|---|---|---|---|
| 랙 입구 평균 | 19.33도 | 20.52도 | 22.18도 |
| 랙 입구 최대 | 23.68도 | 28.89도 | 30.87도 |
| 줄 끝 평균 / 가운데 평균 | 22.30 / 18.59도 | 25.34 / 19.32도 | 29.13 / 20.44도 |
| 줄 끝 - 가운데 | 3.71 K | 6.02 K | 8.69 K |
| 랙별 오차 RMSE, 상관 | 3.83도, 0.86 | 2.71도, 0.84 | |
| CRAC로 나가는 열(발열 600 kW) | 약 500 kW | 584 kW | 600 kW |
| 방 윗부분(2 m 이상) 평균 | 약 24도 | 31.5~33도 | 31.2~31.5도 |

정상 상태(새는 공기가 없는 시나리오)는 이 수정의 영향이 없다(RMSE 0.65도 그대로). 계산 시간은 약 6.6초로 거의 같다.

**남은 차이와 추측**
- 바닥 근처(높이 0~1 m)가 OpenFOAM보다 차갑다(우리 23.5~24.3도, OpenFOAM 26.3~27.2도). OpenFOAM에서는 난류 혼합과 급기 제트의 끌어들임으로 방 위의 뜨거운 공기가 아래까지 내려오는데, 우리 모델은 위쪽에 쌓여 있다(추측).
- 혼합 계수 `K_DIFF`를 올려 봤다(0.05, 0.1, 0.2). 평균은 맞아 가지만 줄 끝과 가운데의 차이가 사라져 RMSE가 오히려 나빠졌다(2.84, 3.21, 3.81). 0.02를 유지한다. 한 가지 사례에 맞추는 보정은 과적합 위험이 있어 더 하지 않았다.
- 가장 뜨거운 랙이 OpenFOAM에서는 바깥 줄 끝(Rack_51, 01, 60)이고 우리는 고장 통로 옆 줄(30, 21, 11)이다. 바깥 줄 끝 랙이 방의 뜨거운 공기를 직접 끌어들이는 경로가 우리 모델에는 약하다.
- 다음 후보: 방의 수직 혼합(방 영역에만 더 큰 혼합 계수), 급기구 제트의 끌어들임. 검증용 OpenFOAM 사례가 더 필요하다(다른 CRAC 조합, 랙 배치 변경).

| 시멘틱 세그멘테이션 | ovrtx | uint32 + ID 표 | **직접 확인** | 합성 학습 데이터의 정답(라벨), 장비 마스크 |
| 라이다, 레이더 | ovrtx 센서 | 점군 | 문서에만 있음(미시험) | 필요하면 후속 실험 |
| 물리(강체, 충돌) | ovphysx | 텐서 | 미시험 | 데이터센터에서는 우선순위 낮음 |
| 연기와 유체(Flow) | Kit 확장 | OpenVDB(NanoVDB 변환) | **직접 확인**(내보내기 성공, 용량과 속도 문제 있음) | 시각 효과 후보. 용량 때문에 해상도·채널·빈도를 줄여야 함 |
| Kit 앱 안의 시뮬레이션과 시각화 | Kit SDK 110.4.0 | USD, Warp, OmniGraph | **직접 확인**(RTX 5090에서 실행, Kit 안의 Warp 동작) | 후속: OmniGraph로 센서 값 내보내기 |

## 4. 한계와 다음 단계
- 열 모델은 시각화용이며 응답이 실제보다 매우 빠르다(2.2의 문제 2).
- **CFD는 지금 하지 않는다.** 우리 열 모델(L1)은 정해 둔 공기 흐름 위의 이동과 확산이며, 고체 열 전도와 공기 흐름 계산(L2)은 구현하지 않았다.
- Flow는 우리 데이터센터 열 모델과 연결하지 않았다. 프리셋 기본값(중력 방향, 크기)이 우리 장면에 맞지 않을 수 있다.
- 부피 데이터를 UE로 **가져오는 것(R6)은 확인했다.** 아직 **시간 동기와 값 보존**은 시험하지 않았다.
- 라이다/레이더, ovphysx, OmniGraph로 센서 값을 내보내는 방법은 시험하지 않았다.
- 다음: UE에서 부피를 화면에 그리기, 센서 스트림을 MQTT로 내보내는 생성기, Kit에서 OmniGraph로 센서 값을 내는 방법 확인.
