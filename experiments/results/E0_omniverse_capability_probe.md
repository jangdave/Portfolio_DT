# E0. Omniverse 계열 기술이 주는 데이터 확인 (실증)

- 날짜: 2026-10-15
- 목적: Omniverse 계열 기술에서 **어떤 시뮬레이션 정보와 데이터를 실제로 받아서 쓸 수 있는지** 직접 실행해서 확인한다. (연구 R5의 일부, R1의 준비)
- 관련: [13 Omniverse 연구 계획](../../docs/13_omniverse_research.md), [14 핵심 설계](../../docs/14_sim_to_unreal_core.md)
- 코드와 원본 결과: `experiments/omniverse_probe/`

## 0. 먼저 구분: 무엇을 실행했고, 무엇이 Omniverse Kit인가

| 실행한 것 | 정체 | Omniverse Kit인가 |
|---|---|---|
| Warp 1.18.0 | NVIDIA의 GPU Python 시뮬레이션 라이브러리 | **아니다.** Omniverse와 같은 NVIDIA 계열이지만 Kit 앱 안에서 돈 것이 아니다. |
| ovrtx 0.3.0 | Omniverse의 렌더링 라이브러리(Python) | **아니다.** Omniverse 라이브러리이며 Kit 앱이 아니다. |
| usd-core | OpenUSD Python 라이브러리 | 아니다. |
| **Omniverse Kit SDK** | Kit 앱을 만드는 개발 기반 | **아직 설치·실행하지 않았다.** NVIDIA 라이선스 약관 동의가 필요해 확인을 기다리는 중이다. |

따라서 아래 결과는 "**Omniverse Kit에서 본 결과**"가 아니라 "**Omniverse 계열 라이브러리(Warp, ovrtx)로 만든 결과**"다. Kit에서의 확인은 R1(설치)과 R2(Flow) 이후에 한다.

## 1. 환경
RTX 5090 32GB, 드라이버 CUDA 13.4, Python 3.13.9, Warp 1.18.0(CUDA Toolkit 13.4, sm_120), ovrtx 0.3.0.312915, ovphysx 0.3.7, usd-core 26.8

## 2. 결과

### 2.1 Warp가 RTX 5090에서 동작한다 (직접 확인)
- Warp가 GPU를 `sm_120`(Blackwell)으로 인식하고 커널을 컴파일해 실행했다. 첫 컴파일 0.43초, 계산 결과 일치.

### 2.2 USD 장면 위의 열 시뮬레이션과 가상 센서 (직접 확인)
`thermal_poc.py`: 랙 10기, CRAC 2기, 센서 앵커 24개가 있는 USD 장면을 직접 만들고, **그 USD에서 형상과 앵커 위치를 읽어** Warp로 계산했다.

| 항목 | 값 |
|---|---|
| 장면 | 8 x 6 x 3.5 m, 랙 2줄 x 5기, 마주 보는 찬 통로, 양 끝 CRAC 1기씩 |
| 격자 | 10 cm 간격, 80 x 60 x 35 = 168,000칸 |
| 시나리오 | 240초, 60초에 CRAC_02 팬이 멈춤 |
| 센서 ID | 규격 규칙(`H01-RK01-TEMP-IN`)대로 USD 경로에서 계산 |
| 가상 센서 | 앵커 위치에서 온도를 세 선형 보간으로 읽음, 24개 x 240초 = 5,760개 값 |

**결과(랙 입구 온도, 마지막 10초 평균, 서쪽 → 동쪽)**

| 줄 | 서쪽 ← | | | | → 동쪽 (고장난 CRAC_02 쪽) |
|---|---|---|---|---|---|
| Row01 (RK01~05) | 22.5 | 23.6 | 27.4 | 40.1 | 42.4 |
| Row02 (RK06~10) | 22.5 | 23.5 | 27.3 | 39.7 | 41.9 |

- 정상일 때(고장 전) 입구 온도 평균은 약 21.5도였다.
- **고장난 CRAC에 가까운 동쪽 랙 4기가 고장 후 6~8초 만에 27도를 넘었다.** 서쪽 랙은 CRAC_01이 작동해 22~24도로 유지됐다.
- 센서별 시계열은 `out/thermal_sensors.csv`, 온도 단면 이미지는 `out/thermal_slice_t*.png`.

**이 실험에서 찾은 문제 두 가지**
1. **센서 위치 오류(수정함):** 처음에는 모든 랙이 똑같이 31.3도로 나왔다. 앵커를 **스케일이 걸린 랙 상자의 자식**으로 만들어서 월드 좌표에 랙의 스케일이 곱해졌기 때문이다. [USD 규격](../../docs/09_usd_spec.md) 2장의 "장비는 스케일 없는 Xform, 모양은 자식 메시" 규칙이 필요한 이유를 실제로 보여 준 사례다.
2. **응답이 너무 빠르다(미해결, 한계):** 실제 시설의 열 반응은 분 단위인데 이 모델은 6~8초 만에 변한다. 시각화용으로는 시간 배율이나 열 질량 매개변수로 조정할 수 있지만 **이번에는 조정하지 않았다.**

### 2.3 계산 속도와 해상도 확장성 (직접 확인)
`bench_thermal.py`: 같은 장면을 해상도만 바꿔 GPU 동기화 후 측정했다.

| 격자 간격 | 칸 수 | 시간 간격 | 초당 단계 | 실시간 대비 |
|---|---|---|---|---|
| 10 cm | 168,000 | 0.02 s | 약 43,000 | 약 867배 |
| 5 cm | 1,344,000 | 0.01 s | 약 45,000 | 약 452배 |
| 2.5 cm | 10,752,000 | 0.0025 s | 약 5,500 | 약 13.7배 |

- 이 규모의 시뮬레이션은 GPU에게 부담이 아니다. 격자를 훨씬 촘촘하게 해도 실시간보다 빠르다.
- **찾은 문제:** 2.5 cm에서 시간 간격을 0.005초로 하니 **계산이 발산**해 NaN이 됐다. 확산의 안정 조건(`K·dt/dx²`)에 여유가 없었다(이론 한계 1/6, 실제로는 0.16에서 발산). 0.1 이하(실제 0.08)로 맞추니 안정적이다. **이 값을 규칙으로 문서화한다.**
- 계산 속도에는 GPU 캐시 효과가 섞여 있어 대역폭 같은 추정치는 이 표에 넣지 않았다.

### 2.4 NanoVDB 저장과 다시 읽기 (직접 확인)
- `wp.Volume.load_from_numpy`로 온도장을 만들고 `save_to_nvdb`로 저장, `load_from_nvdb`로 다시 읽어 복셀 수와 간격이 같음을 확인했다.
- 파일 크기 약 1.1 MB(240초 시점 한 프레임, 80 x 60 x 35, 비압축). 활성 복셀 204,800개는 8x8x8 블록 단위로 채워진 값이다. 이 장면은 꽉 찬 격자라 희소 저장의 이점은 없다.
- **Unreal에서 읽을 수 있는지는 확인하지 못했다**(R6). Warp는 OpenVDB 쓰기를 문서에서 확인하지 못했다.

### 2.5 ovrtx가 주는 렌더 데이터 (직접 확인)
`probe_ovrtx_outputs.py`: 같은 장면에 의미 라벨(랙, CRAC)을 붙여 렌더하고 출력을 모두 받았다. 첫 프레임 0.007초(워밍업 후, 1280 x 720).

| 출력(AOV) | 형식 | 확인한 내용 |
|---|---|---|
| `LdrColor` | 720x1280x4, uint8 | 일반 컬러 이미지 |
| `HdrColor` | 720x1280x4, float16 | 밝기 범위 0.04~407 |
| `NormalSD` | 720x1280x4, float32 | 면의 방향, -1~1 |
| `DepthSD` | 720x1280x1, float32 | 값 범위가 매우 작음(0~0.006). 문서도 "설정에 따라 0일 수 있다"고 적음 |
| `DistanceToCameraSD` | 720x1280x1, float32 | 카메라까지 거리, 1.77~7.77 **m** |
| `DistanceToImagePlaneSD` | 720x1280x1, float32 | 이미지 평면까지 거리, 1.76~6.54 m |
| `DiffuseAlbedoSD` | 720x1280x4, uint8 | 재질 기본 색 |
| `Camera3dPositionSD` | 720x1280x4, float32 | 카메라 기준 3D 위치(배경은 매우 큰 값) |
| `SemanticSegmentation` | 720x1280x1, uint32 | 픽셀마다 라벨 ID |
| `SemanticIdMap` | 바이트 묶음 | ID 대 라벨 이름: `2 = class: rack`, `3 = class: crac` |

- 시멘틱 세그멘테이션이 랙 403,980픽셀, CRAC 128,956픽셀로 장비별로 정확히 분리됐다.
- 단위는 미터다(카메라 높이 3.3 m와 랙까지 실제 거리와 일치).
- 이미지: `out/ovrtx_ldr.png`, `ovrtx_depth.png`, `ovrtx_normals.png`, `ovrtx_semantic.png`

## 3. 받아서 쓸 수 있는 데이터 정리

| 데이터 | 출처 | 형식 | 확인 | 프로젝트에서의 쓰임 |
|---|---|---|---|---|
| 센서 시계열(온도 등) | Warp 가상 센서 | CSV, MQTT 메시지 | **직접 확인** | 실시간 경로(B)로 Unreal에 전달 |
| 온도장(부피) | Warp | NanoVDB | **직접 확인**(저장과 재읽기) | 미리 계산한 부피(C). Unreal 변환은 미확인(R6) |
| 컬러 이미지 | ovrtx | uint8, float16 | **직접 확인** | 비교 렌더(E2), 가상 CCTV 영상 |
| 깊이, 거리, 법선, 알베도, 3D 위치 | ovrtx | float32 | **직접 확인** | 합성 데이터, 거리 측정 |
| 시멘틱 세그멘테이션 | ovrtx | uint32 + ID 표 | **직접 확인** | 합성 학습 데이터의 정답(라벨), 장비 마스크 |
| 라이다, 레이더 | ovrtx 센서 | 점군 | 문서에만 있음(미시험) | 필요하면 후속 실험 |
| 물리(강체, 충돌) | ovphysx | 텐서 | 미시험 | 데이터센터에서는 우선순위 낮음 |
| 연기와 유체(Flow) | Kit 확장 | NanoVDB | **미확인**(Kit 필요) | R2 |
| Kit 앱 안의 시뮬레이션과 시각화 | Kit SDK | | **미확인** | R1. 약관 동의 후 진행 |

## 4. 한계와 다음 단계
- **Kit에서의 결과는 아직 없다.** 지금 결과는 Omniverse 계열 라이브러리만으로 만든 것이다.
- 열 모델은 시각화용이며 응답이 실제보다 매우 빠르다(2.2의 문제 2).
- 부피 데이터를 Unreal에서 읽는 경로(R6)와 시간 동기는 아직 시험하지 않았다.
- 다음: R1(Kit SDK 설치와 실행), R6(NanoVDB → Unreal), 센서 스트림을 MQTT로 내보내는 생성기.

## 5. 다시 실행하기
```
cd experiments\omniverse_probe
uv sync --python 3.13
uv run --python 3.13 python probe_env.py            # Warp와 GPU 확인
uv run --python 3.13 python thermal_poc.py          # 열 시뮬레이션과 가상 센서
uv run --python 3.13 python bench_thermal.py        # 해상도별 속도
uv run --python 3.13 python probe_ovrtx_outputs.py  # ovrtx 출력 (thermal_poc.py를 먼저 실행)
```
`probe_ovrtx_outputs.py`는 종료 시 프로세스가 멈추는 현상이 한 번 있어서(원인 미확인) 결과를 저장한 뒤 바로 종료하도록 했다. 이 때문에 터미널에 출력이 안 보일 수 있으며, 결과는 `out/ovrtx_outputs.json`에 저장된다.
