# 07. 용어집과 문서 작성 규칙

> 이 문서는 누구를 위한 것인가: 이 프로젝트를 처음 보는 개발자, 인수인계를 받는 사람, 그리고 나중의 나.
> 목적: 같은 것을 같은 이름으로 부르고, 어려운 말을 줄여서 문서만 읽고도 작업을 이어갈 수 있게 한다.

## 1. 문서 작성 규칙

1. **쉬운 말을 쓴다.** 어려운 한자어와 외래어 대신 일상적인 표현을 쓴다. (예: "정합성 확보" → "서로 맞는지 확인")
2. **한 개념에 한 이름만 쓴다.** 아래 용어집의 "쓰는 말"을 따른다. 같은 것을 문서마다 다르게 부르지 않는다.
3. **약어는 처음 나올 때 풀어서 쓴다.** 예: "UE(Unreal Engine)". 이후에는 약어를 써도 된다.
4. **문장은 짧게 쓴다.** 한 문장에 한 가지 내용만 담는다.
5. **문서 맨 위에 "무엇에 대한 문서인지, 상태가 어떤지"를 적는다.** 상태는 `초안` / `채택` / `폐기` 중 하나.
6. **결정에는 이유를 적는다.** "무엇을 했다"만 쓰지 말고 "왜 그렇게 했는지, 다른 방법은 무엇이었는지"를 함께 적는다.
7. **날짜는 `2026-10-15`처럼 절대 날짜로 쓴다.** "어제", "최근" 같은 표현은 쓰지 않는다.
8. **모르거나 확인하지 못한 것은 확인하지 못했다고 쓴다.** 추측을 사실처럼 쓰지 않는다.
9. **명령어는 복사해서 그대로 실행할 수 있게** 코드 블록에 쓰고, 어느 폴더에서 실행하는지 적는다.
10. **그림이나 표가 더 쉬우면 쓴다.** 단, 표에는 설명이 짧은 항목만 넣는다.

## 2. 용어집

"쓰는 말"이 이 프로젝트의 표기다. "피하는 말"은 같은 뜻의 다른 표현이라 섞어 쓰지 않는다.

### 프로젝트 / 구조
| 쓰는 말 | 쉬운 설명 | 피하는 말 |
|---|---|---|
| 디지털 트윈 | 실제 시설을 컴퓨터 안에 똑같이 만들고, 센서 값을 받아 상태를 보여 주는 것 | 가상 복제, 쌍둥이 |
| 가상 데이터센터 | 이 프로젝트가 직접 만든, 실제로 없는 데이터센터 | 목업 시설 |
| 운영 화면(클라이언트) | 운영자가 보는 프로그램. Unreal로 만든다 | 프런트, 뷰어(Omniverse 쪽 화면은 "Omniverse 뷰어"로 구분) |
| 시뮬레이션 데이터 | 프로그램으로 만들어 낸 센서 값과 열·기류 데이터 | 가짜 데이터, 모의 데이터 |
| 시나리오 | 정해 둔 상황. 예: 냉각 장치 고장 | 케이스, 이벤트 시퀀스 |
| 센서 | 온도, 전력, 팬 속도 같은 값을 내보내는 가상의 측정 장치 | 계측기 |
| 알람 | 값이 기준을 넘었을 때 운영 화면에 띄우는 경고 | 얼럿, 경보(문서에서는 "알람"으로 통일) |
| 히트맵 | 온도를 색으로 표시한 그림 | 열 지도 |

### 기술
| 쓰는 말 | 쉬운 설명 |
|---|---|
| USD (OpenUSD) | 3D 장면을 담는 파일 형식. 모델, 위치, 설명 정보를 한 구조로 담는다. |
| prim | USD 안의 개별 항목(랙, 서버 등). 경로로 구분한다. 예: `/DC/Hall01/Row01/Rack_01` |
| `dct:` 속성 | 이 프로젝트가 USD 항목에 붙이는 추가 정보. 예: `dct:sensorId` |
| Omniverse | NVIDIA의 3D 제작·시뮬레이션 도구 모음 |
| ovrtx | Omniverse의 렌더링(화면 그리기) 라이브러리. Python에서 USD를 그릴 수 있다. |
| Unreal (UE) | 게임 엔진. 운영 화면을 만드는 데 쓴다. |
| Pixel Streaming | 서버에서 그린 화면을 영상으로 브라우저에 보내는 기능 |
| MQTT | 센서 값을 주고받는 가벼운 메시지 방식 |
| 게이트웨이(Gateway) | MQTT 메시지를 Unreal이 받을 수 있는 형태(WebSocket)로 바꿔 주는 중간 프로그램 |
| WebSocket | 서버와 프로그램이 계속 연결을 유지하며 데이터를 주고받는 방식 |
| VDB | 연기, 기류 같은 부피 데이터를 담는 파일 형식 |
| 미리 계산한 데이터 | 실시간으로 계산하지 않고 먼저 만들어 저장해 둔 데이터. 문서에서 "베이크"라는 말은 쓰지 않는다. |
| 센서 앵커 | USD에서 센서 하나를 나타내는 항목(prim). 센서의 3D 위치와 ID, 측정 종류, 단위를 가진다. |
| 센서 매니페스트 | 모든 센서의 ID, 주소, 위치, 기준값을 모은 JSON 파일. USD 장면에서 자동으로 만든다. |
| 참조(reference)와 덮어쓰기(override) | USD에서 다른 파일의 내용을 가져다 쓰는 것과, 가져온 것의 일부 값만 바꾸는 것 |
| Warp | NVIDIA의 GPU Python 시뮬레이션 프레임워크. 이 프로젝트의 열 시뮬레이션에 쓴다. |
| 가상 센서 | 시뮬레이션 결과에서 센서 위치의 값을 읽어 센서 값으로 만드는 것 |
| NanoVDB | VDB 부피 데이터의 GPU용 형식. Warp가 저장한다. |
| Kit (Omniverse Kit) | Omniverse 앱을 만드는 개발 기반 |
| 1인칭 | 사람의 눈높이에서 보는 시점 |
| 나이아가라(Niagara) | Unreal의 시각 효과(입자) 도구 |
| 시퀀서(Sequencer) | Unreal의 영상·카메라 연출 도구 |
| 외관 | 건물의 바깥 모습. 첫 화면에서 보여 주는 장면 |
| 컷어웨이(단면) | 건물 외벽을 투명하게 하거나 잘라서 안쪽을 보여 주는 표현 |
| 레벨 스트리밍 | 큰 장면의 일부를 필요할 때만 불러오고 내리는 방식 |
| PUE | 전력 효율 지표. 시설 전체 전력을 IT 장비 전력으로 나눈 값. 이 프로젝트에서는 합성한 추정값 |
| 블록아웃 | 크기와 구성만 맞춘 대략적인 모델. 직접 모델링을 시작하는 기준점 |
| 토폴로지 | 3D 모델의 면과 선이 이어진 방식. 휘어지는 모델에서 특히 중요하다. |
| 삼각형 수 | 3D 모델의 복잡한 정도를 나타내는 값. 많을수록 그리는 데 시간이 든다. |
| 히스테리시스 | 기준값 근처에서 알람이 깜빡이지 않도록, 되돌아올 때 여유를 두는 것 |
| 렌더 | 3D 장면을 한 장의 그림으로 그리는 것 |
| VRAM | 그래픽카드 메모리 |
| 지연 | 입력한 뒤 화면에 반영될 때까지 걸리는 시간 |

### 개발 방식
| 쓰는 말 | 쉬운 설명 | 피하는 말 |
|---|---|---|
| 작업 환경 설정 | 규칙, 설정 파일, 점검 스크립트처럼 작업을 돕는 준비물 | 하네스, 스캐폴딩 |
| 회사 자산 분리 규칙 | 재직 회사의 코드·데이터·명칭이 이 저장소에 섞이지 않게 하는 규칙. 파일 이름은 `04_clean_room_policy.md` | 클린룸(처음 한 번만 병기) |
| 동작 확인 테스트 | 기본 기능이 일단 동작하는지 가볍게 확인하는 테스트 | 스모크 테스트(처음 한 번만 병기) |
| 설계 결정 기록(ADR) | 중요한 결정과 이유를 한 장씩 남긴 문서 | |
| 비교 실험 | 두 방식을 같은 조건에서 비교해 숫자로 남기는 일 | 벤치마크 |
| 브랜치 | 본 줄기(`main`)에서 갈라져 나온 작업용 줄기 | |
| 커밋 | 변경 내용을 한 단위로 저장한 기록 | |
| PR(Pull Request) | 내 브랜치를 `main`에 합쳐 달라는 요청. 확인 후 합친다. | 머지 리퀘스트 |
| Squash merge | PR의 여러 커밋을 **하나로 합쳐서** `main`에 넣는 병합 방식 | |
| Milestone | 큰 단계(Phase) 하나를 묶는 GitHub 기능 | 마일스톤(표기만 영어 그대로 써도 됨) |
| Issue | 해야 할 일 한 건 | |
| Git LFS | 큰 파일(그림, 3D, 영상)을 Git에 안전하게 올리는 도구 | |
| Phase | 개발 단계. 번호로 부른다. 예: Phase 1 | 스프린트, 페이즈 |

| 대상 | 규칙 | 예 |

## 4. 인수인계 체크리스트

새로 참여하는 사람이 아래 순서로 읽으면 현재 상태를 파악할 수 있어야 한다.

1. `README.md`: 프로젝트가 무엇이고 어떻게 시작하는지
2. `docs/01_architecture.md`: 전체 구조
3. `docs/02_roadmap.md`: 단계별 계획, GitHub Milestone과 Issue에서 현재 진행 상황
4. `docs/decisions/`: 왜 이렇게 결정했는지
5. `docs/06_workflow.md`: 작업 방식(브랜치, 커밋, PR)
6. `docs/04_clean_room_policy.md`: 지켜야 할 회사 자산 분리 규칙

문서를 고칠 때 이 체크리스트의 순서와 내용이 어긋나지 않는지 같이 본다.

## 5. 기존 문서 정리 방침
- 이미 쓴 문서는 **수정할 일이 생길 때** 이 규칙에 맞게 고친다. 한꺼번에 고치지 않는다.
- 새 문서는 처음부터 이 규칙을 따른다. PR 템플릿에 확인 항목이 있다.
