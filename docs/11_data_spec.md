# 11. 데이터 규격 (센서, MQTT, 게이트웨이)

- 상태: 초안 v1 (2026-10-15). Phase 3 구현 중 숫자와 형식을 조정하고, 바뀌면 이 문서를 먼저 고친다.
- 목적: 센서 값이 만들어져서 화면에 보이기까지 거치는 모든 단계의 약속을 정한다.
- 관련 문서: [09 USD 규격](09_usd_spec.md), [12 Unreal 설계](12_unreal_design.md), [ADR-005](decisions/ADR-005-sensor-anchors-and-manifest.md)

## 1. 전체 흐름

```
[센서 값 생성기]  ──MQTT 발행──▶  [Mosquitto]  ──구독──▶  [게이트웨이]  ──WebSocket──▶  [Unreal]
 (Python, sim/)                    (메시지 중개)           (Node, gateway/)               (운영 화면)
        ▲                                                       │
        │  센서 매니페스트(JSON)                                ├─ 최근 값 보관
        └──────────── USD 장면에서 생성 ─────────────────────────┴─ 알람 판정, 이력 보관
```

| 부품 | 하는 일 |
|---|---|
| 센서 값 생성기 | 시나리오에 따라 센서 값을 만들어 MQTT로 보낸다. |
| Mosquitto | MQTT 메시지를 중개하는 프로그램(브로커) |
| 게이트웨이 | MQTT 메시지를 받아 최근 값을 보관하고, **알람 상태를 판정**하고, Unreal이 받을 수 있게 WebSocket으로 전달한다. |
| Unreal | 값과 알람을 화면에 표시한다. 알람 판정은 하지 않는다. |

알람 판정을 게이트웨이 한 곳에서만 하는 이유는, 판정 규칙이 두 곳에 있으면 서로 어긋나기 때문이다. 또 Unreal 없이도 알람 로직을 시험할 수 있다.

## 2. 센서 ID와 MQTT 주소

규칙은 [09 USD 규격](09_usd_spec.md) 5장에 있다. 요약:

| 항목 | 예 |
|---|---|
| 센서 ID | `H01-RK01-TEMP-IN` |
| MQTT 주소 | `dct/v1/hall01/rack_01/temp_in` |
| USD 경로 | `/DC/Hall01/Row01/Rack_01/Anchors/Sensor_TEMP_IN` |

- 주소의 `v1`은 메시지 형식의 버전이다. 형식이 바뀌면 `v2`로 올리고 둘을 잠시 함께 지원한다.
- 구독할 때는 `dct/v1/#`를 쓴다.

## 3. 센서 매니페스트

USD 장면에서 자동으로 만드는 센서 목록이다. 센서 값을 해석하는 데 필요한 모든 정보가 들어 있고, 생성기, 게이트웨이, Unreal이 모두 이 파일 하나를 기준으로 삼는다.

**파일:** `sim/out/sensor_manifest.json` (생성 결과라 Git에는 올리지 않고, 생성 스크립트로 다시 만든다)

**만드는 법** (저장소 루트에서, 2026-10-15 구현):
```
cd scripts/usd_tools
uv run --python 3.13 python build_manifest.py ../../usd/scenes/hall01.usda ../../sim/out/sensor_manifest.json
```
- 현재 홀(랙 60기, CRAC 8기)에서 센서 204개가 나온다(`rack/temp_in`, `temp_out`, `power` 각 60, `crac/supply_temp`, `return_temp`, `fan_speed` 각 8).
- 센서 ID와 MQTT 주소의 변환은 `scripts/usd_tools/dct_ids.py` 한 곳에만 있고, 검증기와 이 생성기가 함께 쓴다.
- 장면의 `dct:sensorId`가 경로에서 계산한 값과 다르거나 ID, 주소가 중복되면 오류로 멈춘다(테스트: `tests/test_build_manifest.py`, 장면의 센서 수와 매니페스트의 센서 수가 같은지 포함).

```json
{
  "version": 1,
  "hall": "hall01",
  "sensors": [
    {
      "sensorId": "H01-RK01-TEMP-IN",
      "topic": "dct/v1/hall01/rack_01/temp_in",
      "usdPath": "/DC/Hall01/Row01/Rack_01/Anchors/Sensor_TEMP_IN",
      "equipmentPath": "/DC/Hall01/Row01/Rack_01",
      "equipmentType": "rack",
      "metric": "temp_in",
      "unit": "degC",
      "range": [10, 45],
      "warn": 27,
      "critical": 32
    }
  ]
}
```

| 필드 | 설명 |
|---|---|
| `range` | 정상적으로 나올 수 있는 값 범위. 이 밖이면 값이 이상한 것으로 본다(4장). |
| `warn`, `critical` | 주의, 위험 기준. 없으면 알람을 판정하지 않는다. |

**기본 기준값 (시각화용 참고 값)**

| 측정 종류 | 범위 | 주의 | 위험 | 비고 |
|---|---|---|---|---|
| `temp_in` | 10 ~ 45 | 27 | 32 | 데이터센터 입구 온도에 대한 일반적인 권장 범위를 참고한 값. 정확한 기준이 아니다. |
| `temp_out` | 15 ~ 60 | 40 | 50 | |
| `power` (랙) | 0 ~ 15 | 10 | 13 | kW |
| `supply_temp` | 10 ~ 30 | 22 | 26 | |
| `return_temp` | 15 ~ 50 | 35 | 42 | |
| `fan_speed` | 0 ~ 100 | 20 이하 | 5 이하 | 낮을수록 위험(아래쪽 기준, `direction: "low"`) |
| `power` (PDU) | 0 ~ 60 | 45 | 55 | kW |
| `load` | 0 ~ 100 | 80 | 90 | percent |

이 값들은 실제 시설 기준이 아니라 **데모용으로 정한 값**이다. 문서와 화면에 그렇게 표시한다.

## 4. 메시지 형식

### 4.1 MQTT 메시지 (센서 값)
주소 하나에 값 하나를 보낸다. 내용은 JSON이다.

```json
{ "ts": "2026-10-15T09:30:01.250Z", "value": 24.6, "unit": "degC", "quality": "good" }
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `ts` | 문자열 | 값을 만든 시각. UTC, 밀리초까지 (ISO 8601) |
| `value` | 숫자 | 측정값 |
| `unit` | 문자열 | 단위. 매니페스트의 단위와 같아야 한다. |
| `quality` | 문자열 | `good`(정상), `stale`(오래됨), `bad`(고장 의심) |

- MQTT 서비스 품질(QoS)은 0, 보존(retain)은 켠다. 새로 접속한 쪽이 마지막 값을 바로 받을 수 있다.

### 4.2 이상한 값 처리
| 상황 | 게이트웨이의 처리 |
|---|---|
| 값이 `range` 밖이다 | 값은 그대로 전달하되 `quality`를 `bad`로 바꾼다. 알람은 판정하지 않는다. |
| 센서가 일정 시간(기본 5초) 값을 보내지 않는다 | `quality`를 `stale`로 바꿔 알린다. 마지막 값은 유지한다. |
| 형식이 틀린 메시지 | 버리고 로그에 남긴다. 다른 센서 처리에는 영향이 없어야 한다. |
| 단위가 매니페스트와 다르다 | 버리고 로그에 남긴다. |

### 4.3 WebSocket 메시지 (게이트웨이 → Unreal)
JSON 텍스트다. `type`으로 종류를 구분한다.

| `type` | 언제 | 내용 |
|---|---|---|
| `snapshot` | 접속한 직후 한 번 | 모든 센서의 최근 값과 알람 상태 |
| `sample` | 값이 들어올 때마다 | 센서 ID, 값, 단위, 품질, 시각 |
| `alarm` | 알람 상태가 바뀔 때 | 센서 ID, 이전 상태, 새 상태, 값, 시각 |
| `scenario` | 시나리오가 시작·종료될 때 | 시나리오 이름, 시작/종료 |

알람 상태: `normal`(정상), `warn`(주의), `critical`(위험)

```json
{ "type": "alarm", "sensorId": "H01-RK05-TEMP-IN", "from": "normal", "to": "warn",
  "value": 27.4, "ts": "2026-10-15T09:31:12.000Z" }
```

### 4.4 알람 판정 규칙
- 기준을 넘으면 상태가 바뀐다. 다시 정상으로 돌아가려면 기준에서 **여유 값(히스테리시스, 기본 0.5)** 만큼 더 내려와야 한다. 값이 기준 근처에서 흔들릴 때 알람이 깜빡이는 것을 막는다.
- 값이 기준을 넘은 상태가 **2번 연속**일 때만 알람으로 본다(순간 튐 방지). 이 횟수는 설정으로 바꿀 수 있다.

### 4.5 게이트웨이 REST 주소
| 주소 | 내용 |
|---|---|
| `GET /healthz` | 동작 확인 |
| `GET /api/sensors` | 센서 매니페스트 |
| `GET /api/latest` | 모든 센서의 최근 값과 알람 상태 |
| `GET /api/history?sensorId=...&minutes=15` | 최근 이력 (기본 15분 보관, 메모리) |
| `WS /ws` | 실시간 전달 |

## 5. 시간과 재현

- **시간 기준:** 센서 값의 시각(`ts`)은 **생성기가 정한 시각**이다. 게이트웨이와 Unreal은 받은 시각이 아니라 `ts`를 기준으로 이력과 그래프를 그린다.
- **시간 배율:** 생성기에 `--time-scale`(기본 1)이 있어서 시나리오를 빠르게 돌려 볼 수 있다. 배율을 올려도 `ts`는 시뮬레이션 시간 기준으로 일관되게 증가한다.
- **재현:** 생성기는 **난수 시드**를 받는다. 같은 시드, 같은 시나리오, 같은 설정이면 같은 값이 나온다.
- **녹화와 재생:** 게이트웨이는 받은 샘플을 `.jsonl`(한 줄에 샘플 하나)로 녹화하고, `--replay 파일`로 **MQTT 없이도 같은 값을 재생**할 수 있다. 데모를 다른 PC에서 보여 주거나 자동 시험을 할 때 쓴다.

## 6. 센서 값 생성기 (`sim/sensors/`)

### 6.1 시나리오
| 이름 | 내용 | 기대하는 화면 |
|---|---|---|
| `normal` | 전력이 완만하게 오르내리고 온도는 정상 범위 | 알람 없음 |
| `cooling_failure` | 시작 후 60초에 `CRAC_02` 팬이 멈춘다 | 가까운 랙 입구 온도가 올라 주의 → 위험 알람 |
| `power_spike` | 시작 후 30초에 `PDU_03` 담당 랙의 전력이 40% 늘어난다 | 전력과 온도 상승, PDU 부하 알람 |
| `fan_fault` | `CRAC_01` 팬 속도가 40%로 떨어진다 | 팬 속도 알람, 일부 랙 온도가 완만하게 상승 |

센서가 끊긴 상황은 시나리오가 아니라 **고장 주입 옵션**으로 시험한다. 예: `--fault dropout:H01-RK05-TEMP-IN:30s` (30초 동안 값을 보내지 않음)

### 6.2 열 시뮬레이션과 가상 센서 ([ADR-006](decisions/ADR-006-omniverse-based-simulation.md))
센서 값은 **USD 장면 위에서 계산한 열 시뮬레이션의 결과를 센서 위치에서 읽어** 만든다. 상세 설계는 [13 Omniverse 연구 계획](13_omniverse_research.md) 3장에 있다.

| 단계 | 방식 | 역할 |
|---|---|---|
| L0 | 간단한 모델: 냉각이 줄면 입구 온도의 목표값이 오르고, 온도는 목표값을 향해 서서히 변한다(1차 지연, 시간 상수 기본 60초). 출구 온도는 입구 온도에 전력과 냉각량에 비례한 값을 더해 만든다. | **기준선이자 대체 수단** |
| L1 | NVIDIA Warp로 정해 둔 공기 흐름 위에서 열이 이동하고 퍼지는 계산을 하고, 센서 앵커 위치에서 온도를 읽는다. | **목표** |
| L2 | 공기 흐름까지 계산 | 여력이 있을 때 |

- 어느 단계로 만든 값이든 **같은 메시지 형식**(4장)으로 나가므로 게이트웨이와 Unreal은 차이를 모른다. 생성기에 `--solver l0|l1`로 고른다.
- 전력, 팬 속도처럼 열이 아닌 센서 값은 시나리오가 직접 만든다.
- 모든 매개변수(시간 상수, 격자 간격, 열원 세기, 잡음 크기)는 설정 파일에 둔다.
- 교육·시각화용이며 실제 열역학 해석이 아니다.

### 6.3 규모
| 항목 | 값 |
|---|---|
| 센서 수 | 80개 |
| 발행 주기 | 기본 1초 (결정 D4, 측정 후 조정) |
| 초당 메시지 | 약 80개 |
| 게이트웨이 이력 | 15분 x 80개 x 1Hz = 약 72,000개 샘플(메모리) |

이 정도 규모는 한 대의 PC에서 충분히 처리할 수 있을 것으로 예상하지만, **Phase 3에서 실제로 측정**한다.

## 7. 테스트

| 대상 | 방법 |
|---|---|
| 생성기 | pytest. 같은 시드로 같은 값이 나오는지, 시나리오 시작 시점에 값이 변하는지 |
| 매니페스트 | pytest. USD 장면의 센서 수와 같은지, ID와 주소가 규칙과 일치하는지 |
| 게이트웨이 | Node 내장 테스트. 알람 판정(히스테리시스, 연속 횟수), 이상한 값 처리, 형식 오류 |
| 전체 | 녹화된 `.jsonl`을 재생해 Unreal 쪽 화면을 확인(자동 시험은 Unreal 자동화 테스트) |

## 8. 보안 (공개 데모 기준)
- 개발 중에는 로컬(`127.0.0.1`)에서만 연다.
- 외부에 열 때(면접 시연 등)는 [ADR-004](decisions/ADR-004-streaming-hosting.md)의 방식을 따르고, **게이트웨이 WebSocket은 직접 노출하지 않는다.** Pixel Streaming으로 화면만 보낸다.
- MQTT 브로커는 익명 접속을 허용하지 않고, 외부 접속이 필요하면 계정을 설정한다.
- 센서 값은 모두 합성 데이터이므로 개인정보나 회사 정보가 들어가지 않는다.

## 9. 집계 값 (전력량과 효율)

외관 화면과 층 화면에서 보여 주는 **건물 전체 전력, IT 전력, 냉각 전력, 효율(PUE)** 은 개별 센서 값에서 계산한다. 계산은 **게이트웨이 한 곳에서** 한다(알람 판정과 같은 이유).

| 집계 값 | 계산 | 단위 |
|---|---|---|
| `it_power` | 홀의 모든 랙 `power`의 합 | kW |
| `cooling_power` | CRAC 팬 속도로 추정한 냉각 전력의 합(간단한 추정식: 팬 속도에 비례하는 값과 기본 소비의 합) | kW |
| `facility_power` | `it_power` + `cooling_power` + 손실(IT 전력의 일정 비율) | kW |
| `pue` | `facility_power` / `it_power` | 단위 없음 |
| `energy_kwh` | `facility_power`를 시간으로 적분한 누적값(시나리오 시작부터) | kWh |

- **모두 합성한 값이며 시각화용 추정**이다. 실제 시설의 효율 계산이 아니다. 화면에도 "시뮬레이션 값"이라고 표시한다.
- 계산에 쓰는 비율과 추정식의 매개변수는 설정 파일에 둔다.
- WebSocket에 `aggregate` 메시지를 추가한다. 내용: 집계 이름, 값, 단위, 시각. 접속 직후 `snapshot`에도 포함한다.
- MQTT로 발행하지 않는다(게이트웨이가 만든다). REST: `GET /api/aggregates`.
- 옥외 설비 라벨(예: 냉각 전력)에는 같은 집계 값을 쓴다.
