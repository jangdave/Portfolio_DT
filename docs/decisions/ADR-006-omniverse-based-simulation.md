# ADR-006: 시뮬레이션과 데이터는 Omniverse 계열(Warp 포함)로 만든다

- 상태: 채택 (2026-10-15)
- 관련: [08 설계 재점검](../08_design_review.md) P4, D1 / [13 Omniverse 연구 계획](../13_omniverse_research.md) / [ADR-001](ADR-001-roles-omniverse-vs-unreal.md)

## 배경
설계 재점검에서 "센서 값과 열·기류 데이터를 일반 Python이 만들고 Omniverse는 장면 형식과 렌더링에만 쓴다"는 문제를 찾았다(P4). 이 프로젝트에는 **Omniverse 연구가 포함되어야 한다**는 목표가 있어서, 시뮬레이션과 데이터 생성도 Omniverse 계열 기술로 하기로 했다(결정 D1 해결).

## 결정
1. **열 시뮬레이션과 가상 센서는 NVIDIA Warp로 만든다.** USD 장면의 형상과 센서 앵커 위치를 읽어 계산하고, 결과에서 센서 값을 읽는다.
2. 부피 데이터(열·기류 시각화)는 Warp 결과를 NanoVDB로 저장하고 Unreal이 읽는 형식으로 변환한다. Flow(Kit)는 연구 과제(R2)로 시험한다.
3. **Kit 앱은 연구 트랙(R1)** 으로 설치를 시험한다. 성공하면 쓸 부분을 정하고, 실패해도 프로젝트는 진행한다.
4. 간단한 모델(L0)은 **기준선이자 대체 수단**으로 남긴다.
5. 연구 과제 R1~R6을 별도 Milestone로 관리한다.

## 근거
- 센서 값이 "USD 형상 위에서 계산한 시뮬레이션을 가상 센서로 읽은 값"이 되어, Omniverse와 OpenUSD를 쓰는 이유가 분명해진다.
- DSX Blueprint(NVIDIA의 데이터센터 디지털 트윈 참고 구현)도 열·전기 시뮬레이션을 포함하고 Warp를 기술 목록에 둔다. 같은 방향의 참고 사례가 있다.
- 간단한 모델을 기준선으로 남겨서, Omniverse 쪽 작업이 막혀도 일정이 무너지지 않는다.

## 대안
| 대안 | 제외한 이유 |
|---|---|
| 일반 Python 간단한 모델만 사용 | 이 프로젝트의 Omniverse 연구 목표와 맞지 않는다. 기준선으로는 유지한다. |
| 전용 CFD 소프트웨어(FDS, OpenFOAM) | 설정과 학습 비용이 크고 Omniverse 연구와 거리가 있다. 향후 확장 후보 |
| 처음부터 Kit 앱 중심으로 구성 | RTX 5090 지원과 설치 난이도가 확인되지 않았다. 연구 트랙으로 먼저 시험 |

## 위험과 한계
- **Warp 열 시뮬레이션이 의도한 모습으로 나오지 않을 수 있다.** 단계를 L0, L1, L2로 나누고 L0을 기준선으로 둔다.
- **Kit SDK의 RTX 5090 지원이 확인되지 않았다.** R1에서 확인한다.
- **Warp는 OpenVDB 쓰기를 문서에서 확인하지 못했다.** NanoVDB를 변환하는 단계가 필요하며 R6에서 확인한다.
- **ovrtx의 기존 장면 API는 0.4부터 권장되지 않는다.** 현재 0.3.0 버전을 고정해 쓰고, R4에서 새 방식 이전을 시험한다.
- 이 시뮬레이션은 교육·시각화용이며 공학적 정확성을 주장하지 않는다.
